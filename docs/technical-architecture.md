## 0. 아키텍처 개요와 원칙

### 0.1 최상위 설계 명제

> **결정론적 시뮬레이션 코어를 중심에 두고, 그 위에 표현·서비스·서버를 얇게 감싼다.**

이 게임의 모든 게임플레이 규칙은 `mechanics-spec`이 이미 **결정론·정수/고정소수·좌표 키잉 RNG**로 확정했다. 따라서 아키텍처의 핵심 자산은 "규칙을 실행하는 순수 결정론 코어"이며, 나머지(렌더링·입력·네트워크·상점)는 이 코어를 **관측·구동**하는 주변 계층이다. 이 구도는 크로스플랫폼 재사용(→ §12), 서버 검증(→ §6), 리플레이 테스트(→ §11), 방치 캐치업(→ §4)을 동시에 값싸게 만든다.

### 0.2 4대 계층 (Layered Architecture)

```
┌─────────────────────────────────────────────────────────────┐
│  L4. 서버 백엔드 (BaaS/서버리스 우선)                          │
│      계정·인증 / 클라우드 세이브 / IAP 영수증 검증 /           │
│      라이브옵스 리모트 config / 분석 수집 / 푸시               │
└───────────────▲──────────────────────────▲──────────────────┘
                │ (HTTPS, 신뢰 경계)         │
┌───────────────┴──────────────────────────┴──────────────────┐
│  L3. 서비스/포트 계층 (엔진 내, SDK 어댑터)                    │
│      IAP·광고·분석·크래시·푸시·어트리뷰션 SDK 래퍼            │
│      (전부 인터페이스 뒤에 은닉 — 코어는 SDK를 모른다)         │
├──────────────────────────────────────────────────────────────┤
│  L2. 표현 계층 (엔진: 렌더·UI·입력·오디오)                     │
│      코어를 읽기 전용 관측 + 명령 큐에 입력만 적재             │
│      이벤트 버스 구독 (EVT_*), 부동소수 표시값 허용            │
├──────────────────────────────────────────────────────────────┤
│  L1. ★ 결정론 시뮬레이션 코어 (엔진 비의존, 순수)              │
│      일/월 5단계(§4/§5 MS), 명령 큐, 좌표 키잉 PRNG,          │
│      고정소수 산술, 정준 순회, 엔티티 ID 카운터               │
│      — 부동소수·벽시계·비결정 컨테이너 접근 금지               │
└──────────────────────────────────────────────────────────────┘
```

- **설계 결정: L1 결정론 코어는 게임 엔진에 의존하지 않는 순수 모듈로 분리한다.** 엔진 타입(`Vector3`, `Random`, `Time.deltaTime`, `Dictionary` 반복 순서 등)을 코어에서 참조 금지한다. 근거: (1) 엔진 교체·크로스플랫폼(→ §12) 시 코어를 그대로 재사용, (2) 헤드리스로 CI 리플레이·프로퍼티 테스트 실행(→ §11), (3) 서버가 동일 코어를 컴파일해 검증(→ §6) 가능. 코어는 "상태 + 정렬된 입력 로그 → 후속 상태"라는 `[MS §1.1 불변식 D]`를 그대로 물리적 경계로 만든 것이다.
- **설계 결정: 데이터 흐름은 단방향이다. L2/L3는 코어를 읽고 명령 큐에 쓰지만, 코어는 상위 계층을 절대 호출하지 않는다.** 근거: 코어가 UI/네트워크를 읽으면 결정론이 깨진다. 코어의 유일한 외부 입력은 (a) 정렬된 명령 큐(→ §5.2)와 (b) `master_seed`뿐이다.

### 0.3 원칙 요약

| 원칙 | 아키텍처적 함의 | 근거(스펙) |
|---|---|---|
| 결정론 불변식 D | 코어는 `(스냅샷, 명령 로그)`의 순수 함수 | `[MS §1.1]` |
| 무부동소수점 | 코어 전 산술 정수/고정소수, float 정적 분석으로 차단(→ §2.6) | `[MS §1.5, §2]` |
| 좌표 키잉 RNG | RNG 상태 저장 없음(seed+day만), 롤 순서 무관 | `[MS §3, §3.4]` |
| 회사 순서 무관성 | 회사별 독립 처리 → 병렬화 가능(순서는 정준 고정) | `[MS §1.2 DD-19, §9.6 DD-f]` |
| 시뮬=클라이언트, 신뢰=서버 | 사업 신뢰 경계만 서버에, 게임플레이는 클라 | 본 문서 §1.3 |
| 데이터 드리븐 콘텐츠 | 카탈로그·밸런스·문자열=데이터, 코드 분기 없음 | `[GD §12.1], [MS §10.6]` |

## 1. 클라이언트/서버 책임 분담과 기술 스택

### 1.1 신뢰 경계 (Trust Boundary)

F2P + IAP(`README` P2)이고 **비 P2W**(결제는 시간 단축·편의·확장·코스메틱 한정)이며 MVP에 PvP·실시간 경쟁·재화 리더보드가 없다. 따라서 "다른 플레이어에게 피해를 주는 부정"의 표면이 매우 작다. 이 사실이 서버 규모와 안티치트 수위(→ §10)를 좌우한다.

**설계 결정: 시뮬레이션은 클라이언트 권위(client-authoritative), 사업 사실만 서버 권위(server-authoritative)로 분담한다.**

| 책임 | 소재 | 근거 |
|---|---|---|
| 일/월 5단계 시뮬, 진척·완료·정산, 방치 캐치업 | **클라이언트(L1 코어)** | 단일 플레이어 결정론 시뮬은 서버 재실행 이득이 비용을 넘지 않는다. `α_auto`·청산 등은 남을 해치지 않음 |
| 결제 영수증 검증, 엔타이틀먼트(다이아/상품 지급) | **서버** | 매출 직결 — 위조 시 실손해. 클라 신뢰 불가 |
| 클라우드 세이브 저장·계정 귀속 | **서버** | 기기 이전·복구·중복 방지 |
| 라이브옵스 리모트 config·밸런스 버전·A/B 배정 | **서버** | 코드 배포 없이 갱신(→ §7) |
| 분석 텔레메트리 수집 | **서버**(수집 파이프라인) | KPI·A/B 판정(§liveops-analytics 연동) |
| 방치 보상의 경과 시간 산정(온라인 시) | **서버 시각 참조** | 시계 조작 방어(→ §4.4) |
| 골드·자금·명성 등 게임 내 자원 규칙 | **클라이언트** | 게임플레이 자원은 서버 이코노미가 아님(비 P2W) |

- **설계 결정: 게임 내 자원(자금·골드·명성·XP·컨디션·충성도)은 서버가 검증하지 않는다.** 근거: 이들은 실화폐와 교환되지 않고(골드↔자금 주입 불가 `[GD §5.9]`, 다이아=별도 결제 재화 `[README §2.1]`), 조작해도 자기 세션에만 영향한다. 서버 이코노미 검증은 P5(소규모 팀) 대비 과투자다. 단, **결제로 지급되는 다이아·상품 엔타이틀먼트는 서버가 원장을 가진다**(→ §6.1, §10).
- **신뢰 경계의 단일 규칙:** "실화폐가 얽히거나(결제) 계정 간 신뢰가 필요한 것(세이브 소유·복구)만 서버, 순수 게임플레이는 클라이언트." 향후 리더보드·경쟁 콘텐츠가 추가되면 그 부분만 서버 권위로 승격한다(→ §12, §10).

### 1.2 기술 스택 제안 (후보 + 선택 기준)

강제 벤더 없이 **선택 기준**을 먼저 확정하고 후보를 평가한다.

**선택 기준(가중 순):**
1. **결정론 코어 언어의 정수/고정소수 규율** — float 오용을 정적으로 차단할 수 있는가(`[MS §1.5]`).
2. **F2P 모바일 SDK 생태계 성숙도** — IAP·광고·어트리뷰션·분석·크래시(→ §8)를 소규모 팀이 안정 통합.
3. **크로스플랫폼(iOS/Android 우선, 후 PC/웹)** 단일 코드베이스(`README` P1).
4. **소규모 팀 생산성**(P5) — 학습 곡선·에셋 파이프라인·핫리로드.
5. **2D 스타일라이즈드**(밝고 깔끔한 플랫/세미플랫, `README` P3) 렌더 적합성 — 무거운 3D 불필요.
6. 라이선스·비용·장기 유지보수.

**엔진 후보 평가:**

| 후보 | 강점 | 약점 | 결정론 코어 적합성 |
|---|---|---|---|
| **Unity (C#)** | 모바일 SDK 생태계 최강(IAP/Ads/Firebase/attribution 전부 1급 지원), 크로스플랫폼(iOS/Android/PC/WebGL) 성숙, IL2CPP AOT, 대규모 채용 풀 | 런타임 비용·라이선스 변동 이력, 프로젝트 무게 | ★★★ C#로 순수 코어 작성, `int`/`long` 규율 가능. `System.Random`·`float` 금지 애널라이저로 강제 |
| **Godot 4 (C#/GDScript)** | 오픈소스(라이선스 리스크 0), 경량, 2D 성숙, 빠른 반복 | 모바일 F2P SDK(IAP/ads/attribution) 생태계가 얇음 — 상당 부분 자체 통합/플러그인 필요 | ★★★ C# 코어 동일 전략. GDScript는 코어 부적합(코어는 C#) |
| **Flutter/네이티브 UI + 별도 코어** | UI 중심 관리 시뮬에 적합, 접근성/현지화 강함 | 게임 연출·파티클·트랜지션 약함, "게임 느낌" 부족, 게임 SDK 생태계 아님 | ★★ 코어는 Dart/Rust 별도, 검증 필요 |
| **자체 엔진** | 완전 통제 | P5 팀 규모에 비현실적 | — |

- **설계 결정: 1순위 후보로 Unity(C#), 대안으로 Godot 4(C#)를 병기하되, 어느 쪽이든 L1 결정론 코어는 엔진 API를 참조하지 않는 순수 C# 라이브러리로 작성한다.** 근거: (1) SDK 성숙도(기준 2)에서 Unity가 소규모 팀의 통합 부담을 가장 낮춘다 — F2P는 SDK 통합 실패가 곧 매출 손실. (2) 코어를 순수 C#로 격리하면 엔진 결정을 **가역적**으로 만든다 — Unity 라이선스/비용 리스크가 커지면 코어를 그대로 Godot(C#)로 이식(표현·서비스 계층만 재작성). (3) 2D 스타일라이즈드(기준 5)는 두 엔진 모두 충분하므로 렌더가 선택을 좌우하지 않는다.
- **설계 결정: 코어 언어 = C#(엔진과 동일 언어).** 근거: 엔진과 코어의 언어를 통일하면 마샬링/FFI 비용이 없고 소규모 팀이 단일 툴체인으로 개발·디버그·테스트한다. C#는 `long`/`decimal`/체크드 산술과 Roslyn 애널라이저로 float 금지를 컴파일 타임에 강제할 수 있어 `[MS §1.5]`를 값싸게 만족한다. *(대안 고려: Rust 코어 + FFI는 결정론·성능에 이상적이나 P5 팀의 이중 언어 부담이 크다 — post-MVP 재검토, → §14.)*
- **렌더/UI:** 세로(portrait) 우선 UI(`README` P1), 밝은 플랫 2D. 스프라이트/Nine-slice·벡터 아이콘 중심으로 GPU 부하 최소(→ §9). UI 프레임워크는 엔진 표준(Unity UI Toolkit / Godot Control).

### 1.3 계층별 언어·모듈 경계

```
Core.Sim          (C#, 순수, no-engine, no-float)      ← L1
Core.Data         (C#, 스키마·직렬화·마이그레이션)      ← L1/L2 공용
Presentation.*    (엔진 C#: 뷰·바인딩·연출)             ← L2
Services.*        (엔진 C#: IAP/Ads/Analytics 어댑터)   ← L3
Server.*          (BaaS 함수/서버리스, → §6)            ← L4
```

- 의존 방향은 **아래로만**: Presentation → Core, Services → 인터페이스, 절대 역방향 없음.
- `Core.Sim`은 `Core.Data`의 스키마 타입만 알고, 어떤 SDK·엔진 심볼도 링크하지 않는다(CI에서 어셈블리 의존 그래프로 강제 → §11).

## 2. 데이터 모델

`[MS §10]`의 필드 스키마를 저장/런타임 구조로 확정한다. `[MS §10]`이 타입 수준(“저장 표현·인덱싱은 technical 소관”)만 정의했으므로, 본 절이 그 인덱싱·메모리 레이아웃·직렬화를 확정한다.

### 2.1 ID 체계 — 단조 정수 카운터 (결정론 ID)

- **전역 카운터 `next_entity_id : u64`** (`[MS §1.3]`). 엔티티(회사/부서/팀/직원/프로젝트 인스턴스/게시물/꼬리 스케줄 등) 생성 시 현재값 부여 후 +1. **세이브 상태의 일부**(→ §3.1).
- **설계 결정: 단일 전역 카운터를 쓴다(엔티티 타입별 분리 카운터가 아님).** 근거: `[MS §3]` RNG가 `entity_id`로 키잉되므로 ID의 결정론성이 곧 롤의 결정론성이다. 단일 카운터는 "생성이 결정론적 단계 순서(§4/§5 MS) 안에서만 일어난다"는 불변식을 가장 단순하게 보증한다. 타입별 카운터는 타입 간 생성 인터리빙이 순서 의존을 유발할 위험이 있다.
- ID는 **불변·재사용 금지**. 소멸해도 회수하지 않는다(RNG 키 안정성). u64는 장기 세션(수만 일 × 다회사)에도 고갈되지 않는다.
- **런타임 참조:** 엔티티 간 관계는 포인터가 아니라 **ID(`ref<T>`)**로 표현하고, 조회는 타입별 `Dictionary<u64, Index>` 또는 밀집 배열 인덱스로 한다. **단, 반복(iteration)은 절대 이 해시맵 순서로 하지 않는다** — 반드시 §2.2 정준 키로 정렬된 뷰를 순회한다.

### 2.2 정준 순회 순서 (Canonical Iteration Order)

`[MS §1.2]`를 그대로 구현 계약으로 고정한다. 모든 단계의 순회·이벤트 발행·리포트·로그가 이 오름차순을 따른다.

| 집합 | 정렬 키 | 구현 |
|---|---|---|
| 회사 | `slot_idx` (0..9) | 슬롯 배열 인덱스 자체가 순서 |
| 부서(회사 내) | `dept_id` (=개설 순=ID 순) | 정렬된 부서 리스트 유지 |
| 팀(부서 내) | `team_id` | 정렬 리스트 |
| 직원(회사 내) | `employee_id` | 정렬 리스트/인덱스 |
| 게시물 | `posting_id` (상비=부서당 고정 최소 예약 ID) | 정렬 리스트 |
| 프로젝트 인스턴스 | `project_id` | 정렬 리스트 |
| 지원자 | `applicant_index` (0..N−1) | 생성 순 배열 |

- **설계 결정: 각 부모 엔티티는 자식의 "ID 정렬 인덱스 뷰"를 캐시로 유지하고, 삽입/삭제 시 정렬 위치에 갱신한다.** 근거: 매 사이클 순회 시 정렬을 재수행하면 O(n log n)이 반복된다. ID는 단조 증가이므로 새 엔티티는 항상 리스트 끝에 append되어 정렬이 유지된다(삭제는 안정 제거). 이로써 순회는 O(n)이고 순서는 결정론적이다.
- **CI 계약:** 어떤 코드도 `Dictionary`/`HashSet`을 **직접 순회하지 않는다**. 정적 검사로 코어 내 `foreach (var x in someDict)` 패턴을 금지(→ §11).

### 2.3 런타임 데이터 구조 (엔티티·관계)

`[MS §10.1~10.6]` 필드를 런타임 구조로 매핑한다. 관계는 계층(`[GD §3.1]`)을 따른다.

**엔티티 관계 그래프(ID 참조):**
```
Manager(1) ─ gold, slots[10], slot_unlock_flags[10], milestone_flags, master_seed, day
   └─ Company[0..10]  (slot_idx로 정렬)
        ├─ Ledger (자금 원장, month_credit_log, arrears 집계)
        ├─ ReputationLedger (명성 누적)
        ├─ UnassignedPool: Set<ref<Employee>>
        ├─ Employee[]  (employee_id 정렬)
        ├─ Department[1..D_max]  (dept_id 정렬)
        │     ├─ Board (slots[S_board], 상비 예약 슬롯)
        │     ├─ Policy{P1,P2,P3}, mode
        │     └─ Team[0..T_max]  (team_id 정렬)
        │           ├─ leader?: ref<Employee>
        │           ├─ members[]: ref<Employee>
        │           └─ project?: ref<ProjectInstance>
        └─ ApplicantPool (월 갱신)
   (Economy 소유) TailSchedule[]  (release_id 정렬, 회사별)
```

- **설계 결정: MVP는 엔티티당 객체(Array-of-Structs, 참조형/구조체 혼합)로 구현하되, 핫 루프(진행·정산)가 접근하는 필드는 Struct-of-Arrays(SoA) 후보로 표시해 둔다.** 근거: 최대 규모(10사 × 3부서 × T_max팀 × E_max직원)에서도 직원 총수는 수백~수천 단위로 캐시라인 폭발 규모가 아니다. AoS는 소규모 팀의 가독성·디버깅에 유리하다. 성능 측정(→ §9)에서 캐치업 병목이 확인되면 진척·컨디션 등 매일 순회 필드만 SoA로 전환(코어 인터페이스 불변). 조기 SoA는 P5 팀에 과최적화.
- **소유권 준수:** 자원 원장은 단일 소유(`[GD §1.5]`) — 자금=Economy, 명성=Org, 골드/슬롯=Multi. 데이터 구조도 이 소유를 반영해 이중 장부를 코드로 만들지 않는다(예: "총자산"은 파생 계산값이며 저장하지 않음 — 저장 시 이중 진실).
- **파생값 캐시 규칙:** `base_pay`(=Pay(grade,level)), `Cap_team` 등 파생 캐시는 저장하되 **로드 후 재계산 가능해야 하고, 규칙 판정에 재입력 금지**하는 순수 파생만 캐시한다. 부동소수 표시값(총자산 등)은 `[MS §1.5]`에 따라 표시 전용.

### 2.4 저장 표현 (직렬화 스키마)

- **설계 결정: 세이브 직렬화는 스키마 버전이 붙은 이진 포맷(FlatBuffers 또는 MessagePack 후보)을 쓰고, JSON은 디버그/QA 덤프 전용으로만 병행한다.** 근거: (1) 이진은 크기·파싱 속도에서 유리(→ 세이브 빈도 §3.6). (2) FlatBuffers는 스키마 진화(필드 추가/deprecate)에 강해 마이그레이션(→ §3.3)을 돕는다. (3) 결정론상 세이브는 **바이트 재현성**이 있어야 하므로(→ §11 골든 테스트), 직렬화는 정준 순서로 필드를 방출하고 맵 대신 정렬 배열을 쓴다. JSON 텍스트 덤프는 사람이 diff로 회귀를 읽는 용도.
- **정렬 저장:** 모든 컬렉션은 §2.2 정준 키 오름차순으로 직렬화(해시맵 반복 순서 저장 금지 — 로드 시 순서 붕괴 방지).
- **저장 최소 원칙:** `[MS §3.4, §11-⑥]` — RNG 상태 블롭 없음. `master_seed`(u64) + `day`(i64)만이 RNG 상태다. 확정돼 상태에 반영된 롤(성과 등급 `resolved_Q`, 생성된 지원자 카드)은 상태로 저장하고 재롤 금지; 순간형 롤(ε, 퇴사 베르누이)은 저장하지 않는다.

### 2.5 업종 콘텐츠 카탈로그 데이터 스키마 (코드 아닌 데이터)

`[GD §12.1]`·`[MS §10.6]`: **업종 = 데이터 팩, 코드 분기 없음.** 진행·정산 로직은 업종별 `if`를 두지 않고 확장 필드 6종 해석 함수(`[GD §8.3]`)만 평가한다.

**콘텐츠 팩 구조(업종 1종 = 1팩):**

| 스키마 요소 | 필드 | 데이터 형태 |
|---|---|---|
| `industry_def` | id, 표시명 키(l10n), 포지셔닝(기간/분산/선투입/핵심판단 — `[GD §12.5]` 행) | 레코드 |
| `dept_types[3]` | dept_type id, 주 직무 스탯, 부 직무 스탯?(가중 `w_main/w_sub`) | 배열(영업부 공통 권장) |
| `catalog[]` | 프로젝트 템플릿(기본 필드 + 확장 6종 `[MS §10.1]`) | 배열, `catalog_id` 정렬 |
| 해석 함수 파라미터 | 시세 `μ`(품목군 3, `amp/period/phase`), 꼬리(`D_tail(Q)/ω`), 감쇠 `δ`(`δ_min/ζ`), 해금 그래프, 성과 등급 절단점 `d_c*`·`σ_hit` | 파라미터 테이블 |
| 경제 데이터 | `C_seed`, `F_found`, `F_found_G` | 스칼라(가드레일 `[GD §5.8]` 충족은 balance 검증) |

- **설계 결정: 확장 필드 "보상 계수 소스·해금 조건·완료 부가 효과"는 문자열 코드가 아니라 닫힌 enum + 파라미터 참조로 직렬화한다.** 근거: `[GD §8.3]`이 이들을 **닫힌 목록**으로 확정했다(신설은 스키마 개정 선행). enum + 파라미터 테이블은 코어가 임의 코드를 로드·실행하지 않으면서(스토어 정책·보안 §10 준수) 데이터만으로 업종을 추가하게 한다. 해금 술어는 "완료 이력 술어(+성과 문턱?)" / "동적 상태 술어(활성 꼬리 보유 자사 출시작 존재)"의 2계열 파라미터화된 조회식으로만 표현.
- **팩 로딩:** 콘텐츠 팩은 addressable 에셋/리모트 번들로 로드(→ §7). 팩은 **버전 태그**를 가지며 세이브에 핀(→ §7.3)되어 결정론을 보존한다.
- **업종 추가 = 팩 추가.** 시스템 코드(§5~§11 규칙) 불변 `[GD §12.8]`. 신규 업종이 확장 6종으로 표현 불가하면 그것은 팩이 아니라 `[GD §8.3]` 개정 안건이다(코어 변경 필요 → CI 계약 위반).

### 2.6 고정소수·화폐 산술 구현 (`[MS §2]` 확정)

본 문서가 `[MS §11]`에 따라 확정해야 하는 정밀도 규약:

- **고정소수 스케일 `FP = 1_000_000`** (Q값 = 실수 × 10⁶, `i64`(C# `long`) 보관). `PROB_ONE = 1_000_000`. 곱셈 `(a*b)/FP`, 나눗셈 `(a*FP)/b`. **모든 팀·플랫폼이 동일 스케일·동일 연산 순서.**
  - **오버플로 관리:** `a*b` 중간값이 `i64` 범위를 넘을 수 있는 다중 곱(보상식 `M×v_post×m_Q×coef×α_auto`)은 **`i128`(또는 `System.Int128`/직접 128비트 곱) 중간 누산 후 마지막에 1회 `/FP`·정수화**한다. 근거: `[MS §2.1]` "중간 반올림 누적 금지 + 원장 기입 직전 1회 정수화".
- **반올림 = round-half-away-from-zero(=round-half-up, 게임 값 ≥0이므로 0.5 올림).** 화폐성 최종 트랜잭션의 유일 규칙. 구현:
  ```
  round_half_up_div(num, den>0):  # num≥0
      return (num + den/2) / den   # 정수 나눗셈
  ```
- **최대 잉여법(largest-remainder)** — 꼬리 분할(`daily[]`)·XP 지분·레벨 스탯 분배에서 "정수 합 = 총액" 보장:
  ```
  largest_remainder(total, weights[]):
      raw_i = total * weights[i] / Σweights   (내림)
      rem_i = 나머지
      부족분 = total − Σ raw_i
      rem 내림차순(동률 시 인덱스 오름차순)으로 부족분만큼 +1
  ```
  동률 타이브레이크는 **인덱스 오름차순**으로 고정(결정론).
- **부동소수 금지 강제:** `Core.Sim`/`Core.Data`에서 `float`/`double`/`System.Random`/`DateTime.Now` 심볼 사용을 **Roslyn 애널라이저 + 어셈블리 의존 검사**로 컴파일 실패시킨다(→ §11). 표시 전용 파생값은 표현 계층(L2)에서만 float화.

## 3. 세이브/로드 시스템

### 3.1 무엇을 저장하는가 — 결정론 기반 최소화

세이브 = **전체 게임 상태 스냅샷**. 결정론 덕에 "재현에 필요한 것"이 최소화된다:

**저장 대상(진실의 원천):**
- 경영자 레이어: `gold`, `companies[]`, `slots[10]`, `slot_unlock_flags[10]`(비가역), `autonomy_unlocked`, `milestone_flags[M1..M15]`, 완주 이력(업종별), **`master_seed`, `day`, `next_entity_id`**.
- 회사/부서/팀/직원/프로젝트 인스턴스/보드/게시물 전체 필드(`[MS §10]`).
- 경제 원장: 잔액·`arrears`·`unpaid_upkeep`·`month_credit_log`·활성 꼬리 스케줄(`daily_amount[]` 사전 정수화).
- **확정된 롤 결과**: `resolved_Q`, 생성된 지원자 카드, `v_post`(게시 시 고정).
- 콘텐츠 버전 핀·밸런스 버전 핀·A/B 배정(→ §7.3).

**저장하지 않는 것:**
- RNG 상태 블롭(`master_seed`+`day`가 대체 — `[MS §3.4, §11-⑥]`).
- 순간형 롤(ε, 퇴사 베르누이) — 필요 시 좌표로 재계산.
- 파생 표시값(총자산 등), 파생 캐시 중 재계산 가능분(로드 후 rebuild 허용).

### 3.2 스냅샷 vs 명령 로그 — 트레이드오프 확정

`[MS §12-7]`(열린 질문)·`[MS §11-⑤]`가 남긴 "입력 로그 누적 vs 주기적 스냅샷"을 확정한다.

| 방식 | 로드 비용 | 크기 | 재현·검증 | 판정 |
|---|---|---|---|---|
| 순수 리플레이(seed+전체 명령 로그) | 세션 길수록 O(전체 일수) 재계산 — 부팅 지연 폭발 | 로그 무한 증가 | 완벽 | ✗ 단독 사용 불가 |
| 전체 스냅샷만 | O(1) 로드 | 상태 크기 고정 | 검증엔 로그 필요 | 로드엔 최적 |

- **설계 결정: 로드의 진실의 원천은 전체 스냅샷이다. 명령 로그는 별도의 append-only 리플레이 로그로 유지하되, 통상 로드 경로에는 쓰지 않는다.** 근거: (1) 확정 롤을 상태에 저장(`[MS §3.4]`)하므로 스냅샷만으로 완전 복원되어 부팅이 O(1)이다. (2) 순수 리플레이는 장기 세션에서 부팅 지연을 만든다(`[MS §12-7]`의 우려). (3) 그럼에도 리플레이 로그는 **버렸을 때 잃는 것**(결정론 회귀 테스트·서버 검증·버그 재현)이 크므로 유지한다.
- **명령 로그 정책:** 마지막 스냅샷 이후의 명령만 링버퍼로 보관(스냅샷 시점에 truncate). CI 골든 테스트·QA 버그 리포트는 "seed + 시작 스냅샷 + 이후 로그"를 첨부(→ §11). 저장은 로컬 우선, 옵트인 시 서버 업로드(→ §6, 프라이버시 §6.3).
- **체크포인트:** 세이브 자체가 곧 체크포인트다(→ §3.6 빈도). 방치 캐치업(→ §4)은 명령이 없는 순수 sim advance이므로 로그도 짧다.

### 3.3 세이브 포맷과 버전 마이그레이션

- **포맷:** 헤더(`magic`, `save_schema_version`, `content_pack_version`, `balance_version`, `app_build`, `created_at`, `payload_len`, `hmac`) + 이진 페이로드(§2.4) + 무결성 태그(§3.4).
- **버전 3종 분리(중요):**
  1. `save_schema_version` — 저장 구조 형태. 마이그레이션 대상.
  2. `content_pack_version` / `balance_version` — 결정론 재현용 핀(→ §7.3). 마이그레이션과 별개.
  3. `app_build` — 진단용.
- **설계 결정: 마이그레이션은 버전 N→N+1 단조 변환 체인으로 구현하고, 각 스텝은 순수 함수 + 골든 테스트를 갖는다.** 근거: 소규모 팀이 임의 버전 간 점프 변환을 유지하는 것은 비현실적. 단조 체인(N→N+1→…→현재)은 각 스텝만 검증하면 임의 구버전을 안전히 승급한다. 결측 필드는 기본값 규칙(스키마에 명시), 제거 필드는 무시.
- **결정론과 마이그레이션의 상호작용(핵심):** 세이브 구조가 바뀌어도 `master_seed`·`day`·`entity_id`·확정 롤은 보존해야 재현이 유지된다. 마이그레이션이 밸런스/콘텐츠 파라미터를 바꿔야 한다면 그것은 **콘텐츠 버전 핀 변경**이며 리플레이 로그를 무효화한다(로그에 콘텐츠 버전 경계를 기록 → §11 리플레이 테스트가 경계에서 분리).

### 3.4 무결성·변조 방지

- **설계 결정: 로컬 세이브에 HMAC-SHA256 서명을 붙인다. 키는 기기 보안 저장소(iOS Keychain / Android Keystore)에서 파생하고, 클라우드 세이브의 최종 권위는 서버가 가진다.** 근거: 로컬 서명은 순진한 파일 편집을 막고, 게임플레이 자원은 서버 검증 대상이 아니므로(§1.1) 강한 봉인은 불필요하다 — 자기 세션 조작은 남을 해치지 않는다. **결제 엔타이틀먼트(다이아·상품)는 세이브가 아니라 서버 원장이 권위**이므로(§6.1) 세이브 위조로 유료 재화를 얻을 수 없다. 이것이 방어 수위 결정의 핵심(→ §10).
- 서명은 변조 **탐지**용(재미 보호·지원 진단)이지 완전 방지 주장 아님. 루팅 기기에서 로컬 봉인은 결국 우회 가능하므로, 방어의 무게는 실손해 표면(결제·클라우드)으로 이동시킨다.

### 3.5 클라우드 세이브·계정 연동

- **계정 모델:** 게스트(기기 로컬, 익명 ID) → 플랫폼 계정 연동(Sign in with Apple / Google Play Games / 커스텀). 연동 시 서버가 세이브를 계정에 귀속.
- **동기화:** 서버 세이브에 `save_version`(단조 증가 카운터) + 서버 타임스탬프. 충돌 시 규칙: **더 진행된(day/version 큰) 쪽 우선 + 사용자 확인 프롬프트**(자동 병합 없음 — 단일 세이브 게임이라 병합은 위험).
- **다기기:** "쓰기 토큰"으로 마지막 활성 기기 표시, 이관 시 재확인. 오프라인 편집 후 온라인 시 서버가 버전 비교로 롤백/승급 판정.
- **복구:** 계정 재로그인으로 서버 스냅샷 pull. 삭제 요청(프라이버시 §6.3) 시 서버 세이브·분석 PII 삭제.

### 3.6 세이브 크기·빈도

- **크기 추정:** 최대 규모(10사 × ~수백 직원 × 프로젝트·게시물·꼬리)에서 이진 스냅샷은 수십 KB~수백 KB 규모(문자열은 l10n 키로 참조, 카탈로그는 팩 참조라 세이브에 미포함). 압축(LZ4/zstd) 적용.
- **설계 결정: 세이브 트리거 = (a) 앱 백그라운드 전환 (b) 월말 정산 완료 (c) 결제/설립/청산 등 중대 상태 변화 (d) N분 주기 오토세이브. 클라우드 업로드는 디바운스(백그라운드/월말/결제 시)로 제한.** 근거: 사이클마다 클라우드 쓰기는 대역·배터리·서버비 낭비. 로컬은 자주(크래시 대비), 클라우드는 의미 있는 경계에서만. 방치 게임 특성상 백그라운드 전환이 가장 중요한 트리거다.

## 4. 오프라인/방치 진행 (캐치업)

`README` P1: "자율 주행 방치 플레이"가 핵심. 앱 종료 중 경과 시간을 **결정론적으로 재계산**해 자율 부서가 방치 중 프로젝트를 굴린 결과를 복원한다.

### 4.1 캐치업 모델 — 결정론 재계산

핵심 통찰: **방치 구간에는 플레이어 명령이 없다(명령 큐가 비어 있다).** 따라서 캐치업은 "명령 없는 `advance_one_cycle()`의 반복"이며, 자율 주행(§2단계)만 프로젝트를 굴린다. 결정론이므로 결과는 유일하다.

```
resume(now_trusted):
    elapsed_days = compute_elapsed_days(last_saved_time, now_trusted)   # §4.4 시각 신뢰
    n = min(elapsed_days, DAY_OFFLINE_CAP)                              # 상한 §4.3
    fast_forward(n):
        repeat n times:
            advance_one_cycle()      # 명령 큐 빈 상태, 렌더 없음(헤드리스)
    present_catchup_summary()        # 그 사이 완료·정산·알림 요약 표시
    if elapsed_days > n: note_capped()
```

- **결정론 보증:** `advance_one_cycle`은 `[MS §4.1]` 그대로. 자율 선택(`[MS §6]`)은 무난수·완전 결정론이고, 롤(ε·퇴사·보드 보충·지원자)은 좌표 키잉이라 **오프라인에서 재계산해도 온라인에서 진행했을 때와 동일**하다. 즉 "방치 결과 = 실시간으로 켜 두었을 결과"가 바이트 단위로 일치한다.
- **명령 없음의 함의:** 자율 부서는 `C₀=0` 콘텐츠만 수행(자금 무지출 `[GD §9.5]`)하므로 방치 중 회사가 잔액을 소진해 자멸하지 않는다(자율 생존 가드레일 `[GD §5.8-2]`). 수동 부서·미해금 자율은 방치 중 프로젝트를 착수하지 않는다(팀 유휴 유지, 컨디션 회복만).

### 4.2 리플레이 vs 스냅샷 (캐치업 맥락)

- 캐치업은 **스냅샷에서 출발해 n사이클 순수 전진**한다. 리플레이 로그가 필요 없다(방치 구간에 입력이 없으므로).
- 대안(사전 계산 vs 부팅 시 계산): **부팅 시 계산**을 택한다. 근거: 방치 결과는 경과 시간에 의존하므로 사전 계산 불가. 다만 상한(§4.3)과 헤드리스 최적화(§4.3)로 부팅 지연을 통제한다.

### 4.3 경과 시간 상한·부팅 성능

- **설계 결정: 방치 진행에 상한 `DAY_OFFLINE_CAP`(밸런스 변수, 예: 수 일~수십 일분)을 둔다.** 근거: (1) 무한 방치가 회사를 자동으로 그룹까지 키우면 개입 가치가 사라진다(`[GD §11.1]` 결정 부하 곡선). (2) 부팅 시 재계산 비용 상한. (3) 상한 초과분은 "환영 화면에서 이어서 진행" 유도 → 리텐션. 상한값·초과분 처리(버림 vs 다음 세션 이월)는 `balance.md`/§liveops-analytics와 조율.
- **부팅 캐치업 성능(다수 회사 × 다수 사이클):**
  - **헤드리스 fast-forward:** 캐치업 사이클은 렌더·UI 바인딩·이벤트 UI 반영을 **끄고**, 이벤트는 요약 집계만 한다(개별 EVT를 UI에 흘리지 않음). 순수 정수/고정소수 연산이라 사이클당 수백 µs~ms 목표(→ §9).
  - **회사 병렬화(선택):** 회사는 독립(`[MS §1.2 DD-19]`)이므로 캐치업 시 회사별 스레드 병렬 처리 가능. **단, 이벤트/요약 병합은 정준 슬롯 순서로**, 그리고 프로퍼티 테스트(→ §11 DD-f)가 순서 무관성을 지속 보증할 때만 활성화. 기본은 단일 스레드 결정론, 병렬은 성능 필요 시 켜는 최적화 플래그.
  - **진행률 UI:** 상한 최대치에서도 사용자 체감 지연이 크면 스플래시에 진행 바 + "정산 중" 연출.

### 4.4 시계 조작(치팅) 방어

- **위협:** 기기 시각을 앞당겨 방치 보상을 부당 수확. 비 P2W라 남을 해치진 않지만, IAP(시간 단축 상품)·리텐션 지표를 왜곡할 수 있다.
- **설계 결정: 경과 시간 계산은 온라인 시 서버 시각을 권위로 쓰고, 오프라인 시 단조 시계 + 반되감기(anti-rewind) 워터마크로 방어한다.**
  - **온라인:** resume 시 서버에 시각 질의(또는 세이브 업로드 응답에 서버 타임 포함). `elapsed = server_now − last_saved_server_time`.
  - **오프라인:** 기기 단조 시계(`elapsedRealtime`/`uptime`, 부팅 후 경과)와 벽시계를 함께 저장. 벽시계가 **과거로 점프하면 무시**(음수 delta 거부), **미래로 과도 점프하면 상한(§4.3)으로 클램프**. 마지막으로 본 최대 타임스탬프를 워터마크로 저장해 되감기 탐지.
  - **온라인 복귀 정산:** 다음 접속 시 서버 시각으로 재조정 — 오프라인에 부풀린 진행이 있으면 서버 기준으로 상한 재적용. 서버 시각과의 괴리는 텔레메트리로 로깅(어뷰징 탐지).
- 완전 차단은 불가(오프라인 단일 플레이 특성)하되, **실손해 표면(IAP)은 서버 엔타이틀먼트가 방어**하므로 시계 조작의 실익을 제거하는 데 초점.

## 5. 시뮬레이션 루프 구현

### 5.1 틱 스케줄러

- 시간 모델은 실시간 틱이 아니라 **사이클(일) 기반**(`[GD §2.1]`). "틱"은 벽시계가 아니라 `advance_one_cycle()` 호출이다.
- **구동원 3종:** (a) 플레이어의 "다음 날/진행" 액션 (b) 방치 캐치업 배치(§4) (c) (선택) 자동 진행 모드의 실시간→사이클 매핑(예: 실시간 T초 = 1사이클, UI 옵션). 어느 경우든 코어에 들어가는 것은 동일한 `advance_one_cycle()`이며, 실시간은 표현 계층이 사이클 호출로 변환할 뿐 코어에 들어가지 않는다(결정론 보존).
- **월말 훅:** `day_of_month(day)==30`이면 일 처리 5단계 직후 회사별 `month_end_settle`(`[MS §4.1, §5]`), 정준 슬롯 순서.

### 5.2 명령 큐 (FIFO, 단일)

`[MS §1.4]` 그대로 구현.
- **단일 큐, 제출 순서(FIFO)가 유일 우선순위.** 별도 예약 우선순위 클래스 없음. "예약"은 "다음 사이클 1단계 적용"의 의미일 뿐.
- 큐 원소 = 명령 종류(닫힌 목록 `[MS §1.4]`) + 파라미터(대상 ID·수치). 직렬화 가능(리플레이 로그·서버 검증용 → §3.2).
- **1단계 처리:** `step1_apply_commands`(`[MS §4.2]`) — 제출 순서 순회, 각 명령 `validate→apply` 또는 `EVT_CMD_REJECTED`, 그 후 시스템 재조정(자동 승계), 불변식 assert. 처리 후 큐 clear.
- **월말 예외:** 자진 강등 신청은 1단계가 아니라 월말 4단계에 `pending_self_demotion` 플래그로 소비(`[MS §1.4]`).
- **입력 검증 계층:** 표현 계층(L2)이 UI 가드(버튼 비활성 등)로 1차 필터하되, **최종 재검증은 코어 1단계**가 현재 상태로 수행(reject-on-invalid). UI 낙관적 표시와 코어 확정이 다를 수 있음을 UI가 감수(EVT 구독으로 정정).

### 5.3 이벤트 버스

- 코어는 각 단계에서 `EVT_*`(HIRED, LAUNCH_DIRECT/AUTO, COMPLETE, FAIL, PAID/UNPAID, LEVELUP, QUIT, PROMOTED, BANKRUPT, 마일스톤, ALERT_* 등 `[MS §4/§5]`)를 **정준 순서로 발행**한다.
- **설계 결정: 이벤트는 코어 내부 큐에 정준 순서로 적재되고, 사이클 종료 후 표현/서비스 계층이 배치로 소비한다(코어는 구독자를 콜백하지 않는다).** 근거: 코어가 구독자 콜백을 직접 호출하면 (1) 콜백이 코어 상태를 재진입 변경할 위험, (2) 콜백 실행 순서/부작용이 결정론에 새 위험. "발행=버퍼에 append, 소비=사이클 밖"으로 분리하면 코어는 순수 유지, 표현은 사이클 경계에서 안전 반영. 방치 캐치업(§4)은 이 이벤트 버퍼를 UI로 흘리지 않고 요약만 집계.
- 이벤트는 **관측 사실**이지 상태가 아니다(상태는 엔티티 필드가 진실). 텔레메트리(§8 분석)도 이 버스를 tap.

### 5.4 UI/시뮬 분리 (관측/구독)

- **단방향:** UI는 (1) 코어 상태를 읽기 전용 조회, (2) 이벤트 버스 구독, (3) 명령 큐에 입력 적재 — 이 셋만. UI가 코어 상태를 직접 변경 금지.
- **바인딩:** UI는 사이클 경계에서 관측 스냅샷/델타를 받아 갱신(예: 관측용 read-only view model). 애니메이션·트윈은 표시 전용이며 코어와 무관(결과는 이미 확정).
- **부동소수 경계:** 표시용 파생값(총자산·비율·그래프)은 L2에서 float로 계산 가능(`[MS §1.5]`), 단 규칙에 재입력 금지.

### 5.5 프레임 예산·시분할·병렬화

- **대화형(플레이 중) 한 사이클:** 단일 사이클은 대개 즉시(수 ms) 완료 목표(→ §9). 무거워지면(10사 만재) **시분할**: 사이클 계산을 렌더 프레임과 분리(백그라운드 잡)하고 완료 시 UI 반영. 단, 사이클 내부는 정준 순서로 순차(부분 완료 상태를 UI에 노출하지 않음 — 사이클은 원자적으로 보이게).
- **결정론 vs 병렬:** 회사 간 병렬만 허용(독립 `[MS §1.2]`), 회사 **내부**(부서→팀→직원→프로젝트)는 정준 순서 순차. 병렬 시 이벤트·리포트·원장 로그는 정준 슬롯 순서로 병합. 병렬화는 프로퍼티 테스트(→ §11)가 지키는 한에서만.
- **GC 압력:** 핫 루프에서 힙 할당 최소화(구조체·풀링), 사이클당 할당 예산 설정(→ §9). C# 코어는 `struct` + `Span`/`ArrayPool`로 할당 억제.

## 6. 서버 백엔드

### 6.1 필요한 서버 컴포넌트

| 컴포넌트 | 책임 | 비고 |
|---|---|---|
| 계정/인증 | 게스트→플랫폼 계정 연동, 세션 토큰 | Sign in with Apple/Google 필수(스토어 정책) |
| 클라우드 세이브 | 스냅샷 저장·버전 충돌 해소(§3.5) | 세이브는 불투명 blob + 메타(version/day/time) |
| **IAP 영수증 검증** | App Store/Play 서버 검증, 엔타이틀먼트 원장, 환불·구독 상태 | 매출 직결 — 서버 권위(§10) |
| 라이브옵스 리모트 config | 밸런스/콘텐츠 파라미터·오퍼·A/B 배정 배포(§7) | 버전 태그로 세이브 핀 |

### 6.2 서버리스/BaaS vs 자체 서버 — 선택 기준과 후보

**선택 기준:** P5(소규모 팀) 운영 부담 최소, 위 컴포넌트의 매니지드 제공 여부, KR·글로벌 리전·프라이버시(§6.3), 비용 확장성, 벤더 락인 회피.

| 후보 | 강점 | 약점 |
|---|---|---|
| **BaaS 통합형** (Firebase / AWS Amplify / Supabase) | 인증·저장·리모트 config·분석·푸시·서버리스 함수(영수증 검증)를 매니지드로 한 번에. 소규모 팀 최적 | 벤더 락인, 세밀 제어 한계 |
| **게임 특화 BaaS** (PlayFab / Nakama / GameSparks류) | IAP 검증·엔타이틀먼트·리모트 config·플레이어 데이터가 게임 도메인에 맞춤 | 일부 기능은 자체 확장 필요 |
| **자체 서버** (컨테이너 + DB) | 완전 제어, 락인 없음 | 운영·보안·스케일 부담 — P5에 과함 |

- **설계 결정: BaaS/서버리스 우선(1순위 통합형 BaaS + 필요한 곳만 서버리스 함수), 자체 서버는 회피한다.** 근거: 시뮬이 클라이언트 권위(§1.1)라 서버는 **얇은 신뢰 계층**이면 충분하다 — 무거운 게임 서버가 필요 없다. 영수증 검증·엔타이틀먼트 원장·리모트 config 같은 경계 기능만 서버리스 함수로 두면 P5 팀의 운영 부담이 최소화된다. 락인 완화는 **어댑터 계층(§8)**으로 서버 접점을 인터페이스 뒤에 두어 대비.
- **영수증 검증 흐름:** 클라 결제 → 영수증을 서버 함수로 전송 → 스토어 서버 검증 API 대조 → 엔타이틀먼트 원장 기록·중복 방지(트랜잭션 ID 유니크) → 클라에 지급 승인. 클라는 서버 승인 없이는 유료 재화를 확정하지 않는다.

### 6.3 데이터 프라이버시

- **규제:** KR 개인정보보호법(PIPA), EU GDPR, 미 CCPA/COPPA(아동), 스토어 정책(App Tracking Transparency·데이터 안전 폼). 1차 출시 KR·EN이므로 PIPA·GDPR 우선.
- **원칙:** 데이터 최소 수집, 목적 제한, 동의 기반(어트리뷰션·광고 ID는 ATT/동의 후), 익명/가명 ID 우선, 세이브·분석 PII 삭제 요청 처리 경로(§3.5), 리전 데이터 레지던시 고려.
- **분석 PII 분리:** 텔레메트리는 가급적 비식별(플레이어 pseudo-id). 광고 어트리뷰션(§8)만 동의 하에 기기 식별자 사용.

## 7. 콘텐츠 파이프라인

### 7.1 데이터 드리븐 원칙

코드 배포(스토어 재심사) 없이 갱신 가능해야 하는 것: **밸런스 값(§balance) · 업종 카탈로그(§12) · 현지화 문자열(§accessibility-localization) · 라이브옵스 설정/오퍼(§liveops-analytics, §monetization)**.

- **설계 결정: 이 4종은 전부 코어 밖 데이터로 격리되고, 코어는 이를 파라미터/테이블로 주입받는다.** 근거: `[GD §12.1]` "업종 콘텐츠=데이터, 분기 코드 없음" 원칙을 밸런스·문자열·오퍼로 확장. 데이터/코드 분리가 라이브옵스 민첩성의 전제.

### 7.2 콘텐츠 소스와 갱신 경로

| 콘텐츠 | 소유 문서 | 형태 | 갱신 경로 |
|---|---|---|---|
| 밸런스 값(`α_auto`, `C_seed`, 커브 계수…) | `balance.md` | 테이블(§7.3 버전 핀) | 리모트 config / 번들 |
| 업종 카탈로그·해석 파라미터 | `game-design §12` / 팩(§2.5) | 콘텐츠 팩(addressable/CDN) | 에셋 번들 갱신 |
| 현지화 문자열 | `accessibility-localization` | 문자열 테이블(키 기반) | 번들/CDN, 언어팩 |
| 라이브옵스 설정·오퍼·이벤트 캘린더 | `liveops-analytics`/`monetization` | 리모트 config | 서버 config |

- **로딩:** 앱 기동 시 리모트 config·콘텐츠 매니페스트 fetch → 캐시 → 오프라인 폴백(마지막 정상본). 문자열·카탈로그는 세이브에 미포함(키/버전 참조).
- **스토어 정책 준수:** **실행 코드는 원격 다운로드하지 않는다**(iOS 특히). 데이터(테이블·문자열·팩 파라미터)만 갱신 — 확장 필드가 enum+파라미터인 이유(§2.5).

### 7.3 리모트 config·밸런스 버전 핀 (결정론과의 정합 — 핵심)

**문제:** 밸런스/콘텐츠 값은 `[MS §7]` 결정론 함수의 입력이다. 값이 원격으로 바뀌면 "같은 세이브 + 같은 로그 → 같은 상태"(`[MS §1.1]`)가 깨진다(같은 롤이 다른 결과).

- **설계 결정: 밸런스/콘텐츠 버전을 세이브에 핀(pin)한다. 진행 중 세이브는 생성 시점(또는 명시적 마이그레이션 시점)의 버전으로 계속 시뮬레이션하고, 원격 갱신은 신규 게임 또는 명시적 마이그레이션 경계에만 적용한다.** 근거: (1) 리플레이·서버 검증·버그 재현이 성립하려면 시뮬 입력이 안정해야 한다. (2) 진행 중 세이브의 밸런스를 몰래 바꾸면 플레이어 경험 붕괴(진행 중 회사가 갑자기 적자) + 결정론 회귀. (3) 라이브옵스가 밸런스를 바꾸고 싶으면 **콘텐츠 버전 증가 = 마이그레이션 이벤트**로 명시하고, 그 경계를 리플레이 로그에 기록(§3.3, §11)해 재현 가능성을 구간별로 유지.
- **오퍼·UI·이벤트 캘린더는 시뮬 입력이 아니므로** 진행 중에도 자유 갱신 가능(결정론 무관). 핀 대상은 **시뮬 결과에 영향을 주는 밸런스·카탈로그·해석 파라미터**로 한정한다.

### 7.4 A/B 테스트 훅

- **배정:** 서버가 플레이어 pseudo-id로 안정 배정(같은 유저는 세션 간 동일 그룹). 배정은 세이브에 기록(§7.3 핀과 함께).
- **A/B 대상 분리:** (a) **비시뮬 A/B**(UI·오퍼·가격·튜토리얼 흐름) — 자유 실험, 결정론 무관. (b) **시뮬 A/B**(밸런스 값) — 배정된 밸런스 버전을 세이브에 핀, 그룹 간 밸런스 버전이 다름. 시뮬 A/B는 신규 코호트에 적용(진행 중 세이브 중간 변경 금지, §7.3).
- **측정:** 텔레메트리(§8)에 그룹 태그 부착 → §liveops-analytics가 KPI 판정.

## 8. 서드파티 SDK

- **설계 결정: 모든 SDK는 내부 인터페이스(port) 뒤에 은닉하고, 어댑터(adapter)에서만 실제 SDK를 호출한다. 코어(L1)와 게임플레이는 SDK 심볼을 링크하지 않는다.** 근거: (1) 결정론 코어가 SDK에 오염되면 안 된다. (2) 벤더 교체(락인 회피)·플랫폼별 구현 차이를 어댑터에 격리. (3) SDK 없는 환경(에디터·CI·헤드리스)에서 no-op 어댑터로 테스트.

| SDK 범주 | 통합 지점(포트) | 후보 | 추상화 |
|---|---|---|---|
| **IAP(스토어)** | `IPurchaseService.Purchase/Restore` | Unity IAP / StoreKit·Play Billing 직접 / BaaS 결제 | 결제→서버 검증(§6.1)→엔타이틀먼트. 상품 카탈로그는 데이터(§monetization) |
| **광고(선택)** | `IAdService.LoadRewarded/Show` | AdMob / LevelPlay / AppLovin MAX | 리워드 광고 옵트인만(`README` P2). 보상 지급도 서버 확인 권장 |
| **분석** | `IAnalytics.Track(event, props)` | Firebase / GA4 / Amplitude / 자체 ingest | 이벤트 버스(§5.3) tap. 스키마·KPI는 §liveops-analytics 소유 |
| **크래시 리포트** | `ICrashReporter` | Crashlytics / Sentry | 세이브 버전·seed·day 첨부(재현 §11) |
| **푸시** | `IPushService` | FCM / APNs / BaaS | 방치 복귀·오퍼 알림, 옵트인 |
| **어트리뷰션** | `IAttribution` | Adjust / AppsFlyer / SKAdNetwork | UA 측정(§marketing 연동). 동의(ATT) 후 활성(§6.3) |

- **분석 이벤트 소스:** 코어 이벤트 버스(§5.3)를 어댑터가 구독해 텔레메트리로 변환 — 게임플레이 로직에 `Analytics.Track` 산재 금지(관측 지점 단일화). 크래시 리포트에 `master_seed`+`day`+세이브 버전을 남겨 결정론 재현으로 디버깅(§11).

## 9. 성능·품질 예산

### 9.1 타깃 기기

- **설계 결정: 하한 타깃 = 출시 시점 기준 3~4년 전 보급형(예: 저가 Android, 2~3GB RAM급)까지 60fps UI / 원활한 캐치업. 상한은 프리미엄 기기 고주사율.** 근거: F2P 모바일은 저사양 커버리지가 곧 도달 가능 시장(§marketing UA 효율). 2D 스타일라이즈드라 GPU 여유가 크므로 하한 타깃 달성이 현실적.

### 9.2 예산 항목

| 항목 | 예산(목표) | 근거/전략 |
|---|---|---|
| UI 프레임 | 저사양 60fps(무리 시 30fps 폴백) | 2D 스프라이트·배칭·오버드로 억제 |
| 대화형 1사이클 계산 | 저사양에서 프레임 예산 내(수 ms) | 정수/고정소수 순수 계산, 할당 억제 |
| 캐치업(방치) | 상한(§4.3) 최대치에서도 체감 지연 최소(진행 바 허용) | 헤드리스·요약 집계·(선택)회사 병렬 |
| 다수 회사 시뮬 | 10사 만재에서 사이클당 선형 확장 | 회사 독립(§5.5), SoA 승격 여지(§2.3) |
| 메모리 | 저사양 상주 예산 내 | 세이브 수백KB급, 카탈로그 팩 지연 로드·언로드 |
| 부팅 시간 | 콜드 스타트 목표 수 초 내(+캐치업 별도 표시) | 에셋 지연 로드, 스플래시 중 config fetch |
| 배터리/발열 | 방치 특성상 백그라운드 무연산, 포그라운드 저부하 | 실시간 틱 없음(사이클 기반)이 유리 |
| 에셋 스트리밍 | 업종 팩·직원 초상·아이콘 addressable 온디맨드 | 코드 아닌 데이터(§7), CDN 캐시 |

- **발열/배터리 이점:** 사이클 기반(실시간 물리 틱 없음, `[GD §2.1]`)이라 포그라운드 유휴 시 CPU가 거의 놀 수 있다 — 배속·상시 시뮬이 없어 방치 게임에 유리. "자동 진행" 옵션 사용 시에만 주기 계산.
- **측정 훅:** CI에 헤드리스 벤치(만재 세이브 × N사이클 캐치업 시간·할당) 추가(→ §11), 리그레션 게이트.

## 10. 보안·안티치트

### 10.1 위협 모델과 방어 수위 결정

**설계 결정: 방어의 무게를 "실손해 표면"에 집중하고, 순수 단일 플레이어 시뮬 조작에는 경량 방어만 둔다.** 근거: 비 P2W + MVP에 PvP·재화 리더보드 없음 → 자기 세션 조작은 남을 해치지 않는다. 반면 결제·클라우드는 실손해/신뢰 문제다.

| 위협 | 실손해? | 방어 수위 | 수단 |
|---|---|---|---|
| **영수증 위조/결제 우회** | ★ 매출 직접 손실 | **강** | 서버 영수증 검증 + 엔타이틀먼트 서버 원장 + 트랜잭션 유니크(§6.1). 클라 신뢰 0 |
| **세이브 변조**(자원 수치 조작) | 자기 세션만 | **경~중** | 로컬 HMAC 서명(§3.4). 유료 재화는 세이브가 아닌 서버 원장이 권위라 위조 무익 |
| **시계 조작**(방치 보상) | 리텐션/IAP 지표 왜곡 | **중** | 서버 시각 권위 + 반되감기 + 상한(§4.4) |
| **클라우드 세이브 복제/롤백** | 계정 신뢰 | **중** | 서버 버전 카운터·충돌 해소(§3.5) |
| **리버스 엔지니어링**(콘텐츠 추출) | 낮음 | **경** | IL2CPP AOT·기본 난독화. 과투자 금지 |
| (post-MVP) 리더보드/경쟁 부정 | 도입 시 ★ | **강(도입 시)** | 그 콘텐츠만 서버 권위 승격(§12) |

- **서버 검증 경계:** "실화폐가 얽히거나 계정 신뢰가 필요한 것만 서버가 검증"(§1.1). 게임 내 자원 규칙은 클라이언트가 권위. 이 경계가 P5 팀의 안티치트 투자를 결제·계정에 집중시킨다.
- **결정론의 부가 이점:** 필요 시 서버가 동일 코어로 "seed + 시작 스냅샷 + 명령 로그"를 재실행해 클라 결과를 대조 가능(§3.2). MVP엔 상시 검증은 불필요(비용), **분쟁·어뷰징 탐지용 샘플 검증** 옵션으로 보유.

## 11. CI/테스트 훅

`[MS §11-⑦]` 및 결정론 전제를 CI로 상시 보증한다. 코어가 엔진 비의존 순수 모듈(§0.2)이라 헤드리스 테스트가 값싸다.

| 테스트 | 내용 | 실패 = |
|---|---|---|
| **결정론 리플레이(골든)** | `(master_seed, 시작 스냅샷, 명령 로그)` → 최종 **상태 해시** 고정. 재실행·크로스플랫폼(iOS/Android/에디터, 후 WASM)에서 동일 | 결정론 붕괴(부동소수 혼입·해시 상수 변경·순회 순서 의존) |
| **회사 순서 무관성 프로퍼티(DD-f)** | 임의 `slot_idx` 순열로 월말/사이클 처리해도 **상태 해시 동일**(`[MS §9.6 DD-f]`) | 회사 간 은닉 결합(공유 가변 상태) |
| **세이브 마이그레이션** | 각 `save_schema_version` N→N+1 라운드트립 + 구버전 픽스처 로드→현재 승급 골든 | 마이그레이션 손실/불일치 |
| **부동소수 금지** | Roslyn 애널라이저 + 어셈블리 의존 그래프: 코어에 `float/double/System.Random/DateTime.Now`·엔진 심볼 없음 | 결정론 오염원 유입 |
| **정수/고정소수 항등** | round-half-up·최대 잉여법의 "합=총액" 불변식, 오버플로 경계(§2.6) | 정산 잔차·오버플로 |
| **불변식(assert) 스위트** | 조직 불변식(`[GD §7.5]`)·자원 하한 0·닫힌 유입/유출 목록 검증 | 규칙 위반 |
| **헤드리스 퍼즈/롱런** | 랜덤 명령 스트림 장기 실행 → 크래시·불변식 위반·NaN(있으면 안 됨) 탐지 | 엣지케이스 |
| **성능 벤치**(§9) | 만재 세이브 캐치업 시간·할당 리그레션 게이트 | 성능 퇴행 |

- **상태 해시:** 세이브 스냅샷을 정준 순서로 직렬화해 안정 해시(예: 골든 테스트의 진실값). 바이트 재현성(§2.4)이 전제.
- **빌드/릴리스 파이프라인:** 커밋 → 코어 유닛/프로퍼티/골든 테스트(헤드리스, 빠름) → 엔진 통합 빌드 → 디바이스 팜 스모크 → 소프트런치 채널 → 글로벌(§production-qa-risk가 일정·게이트 소유). 콘텐츠 팩·리모트 config는 앱 빌드와 분리 배포(§7)하되 스키마 호환 검사를 게이트로.
- **QA 재현:** 크래시/버그 리포트에 `master_seed`+`day`+세이브 버전+명령 로그 첨부 → 로컬에서 결정론 재현(§8 크래시 첨부). 이 재현성이 소규모 QA 팀의 최대 레버리지.

## 12. 크로스플랫폼 확장 경로

`README` P1: 런치는 모바일, 아키텍처는 PC/웹 확장 여지 유지.

- **재사용의 핵심:** L1 결정론 코어는 엔진·플랫폼·입력 비의존(§0.2)이라 **PC/웹으로 그대로 이식**된다. 세이브 포맷·시뮬 결과가 플랫폼 간 동일(정수/고정소수라 부동소수 편차 없음) → **크로스 세이브·크로스 플레이 가능**.
- **플랫폼별로 바뀌는 것(표현·서비스만):**
  - 입력: 터치 → 마우스/키보드/게임패드. 명령 큐 인터페이스는 동일.
  - 레이아웃: 세로(portrait) → 가로(landscape)/창. UI Toolkit 반응형으로 흡수(정보구조는 §ux-design).
  - 스토어/SDK: 모바일 IAP → Steam/에픽/웹 결제. 어댑터(§8) 교체로 격리.
- **웹(WASM) 주의:** Unity WebGL / Godot Web export로 코어를 WASM 컴파일 시 **결정론 재검증 필수** — WASM은 정수/비트 연산이 결정적이므로 부동소수 금지(§2.6)를 이미 지켰다면 안전하나, 골든 테스트(§11)를 WASM 타깃에도 돌려 상수·산술 일치를 보증한다.
- **경쟁 콘텐츠 도입 시(post-MVP):** 리더보드·비동기 경쟁이 생기면 그 부분만 서버 권위로 승격하고, 결정론 코어의 서버 재실행 검증(§10.1, §3.2)을 활성화한다 — 코어가 이미 결정론이라 이 승격이 값싸다.

## 14. 열린 질문

본 문서는 game-design·mechanics-spec의 규칙·결정론 전제를 기술 아키텍처로 확정했다. 아래는 스파이크·프로토타입·플레이테스트로 답할 **기술 수준** 질문이다(규칙 질문은 `[GD §15]`, 구현 스펙 질문은 `[MS §12]` 참조).

1. **해시 PRNG 최종 선택(§13-①)** — SplitMix64 파이널라이저 vs xxHash64 vs PCG의 분포 품질·좌표 키잉 편향·모바일/WASM 성능. 6좌표(seed+stream+4)를 하나의 64비트로 믹싱할 때 저비트 상관 여부. **런치 전 동결 필수**(교체 시 전 세이브 리플레이 비호환).
2. **`FP=10⁶` 충분성 vs Q32.32(§13-②, `[MS §12-2]`)** — `μ`·`q_raw`·`e`·복리형 곱(`ζ^n`, `φ^s`)의 게임 최대 기간 누적 반올림 오차 측정. `i128` 중간 누산으로 오버플로는 막히나, 정밀도 부족이 밸런스 가드레일(`[GD §5.8]`) 경계에서 등급 역전을 일으키는지.
3. **코어 언어: 순수 C# vs Rust+FFI** — 결정론·성능은 Rust가 우위이나 P5 팀 이중 언어 부담. C# 단일이 크로스플랫폼(특히 WASM)에서 충분한 결정론·성능을 주는지 벤치 필요.
4. **회사 병렬 캐치업의 실효(§4.3·§5.5)** — 10사 만재 캐치업에서 단일 스레드로 예산(§9)을 만족하는가. 병렬화가 필요할 만큼 무거운가, 아니면 프로퍼티 테스트 유지 비용이 더 큰가.
5. **`DAY_OFFLINE_CAP` 값과 초과분 처리(§4.3)** — 상한값·초과분(버림 vs 이월)이 리텐션·IAP(시간 단축)·개입 가치(`[GD §11.1]`)와 어떻게 상호작용하는지 — `balance.md`·§liveops-analytics·§monetization 공동 확정.
6. **밸런스 버전 핀의 라이브옵스 마찰(§7.3)** — 진행 중 세이브 밸런스 불변 원칙이 밸런스 핫픽스(치명적 exploit·소프트락)를 막을 때의 예외 절차. "긴급 마이그레이션" 경계를 얼마나 매끄럽게 만들 수 있는지.
7. **BaaS 벤더 선택·락인(§6.2)** — 통합형 BaaS vs 게임 특화 BaaS의 KR/글로벌 리전·PIPA·비용·영수증 검증 성숙도 대조. 어댑터 계층이 실제 이관을 얼마나 값싸게 하는지 PoC.
8. **세이브 직렬화 포맷(§2.4)** — FlatBuffers(스키마 진화·제로카피) vs MessagePack(단순·유연)의 크기·마이그레이션 용이성·바이트 재현성 대조.
9. **엔진 최종 결정 시점** — Unity vs Godot 결정을 코어(엔진 비의존) 프로토타입 이후로 미룰 때, 표현 계층 착수 지연이 P5 일정(§production-qa-risk)에 주는 영향. 코어 격리가 이 지연을 얼마나 흡수하는지.
10. **상태 해시 함수(§11)** — 골든/프로퍼티 테스트의 상태 해시가 스키마 진화(§3.3)에 견고하려면 어떤 정규화가 필요한지(파생 캐시 제외·정준 직렬화 범위).
11. **서버 샘플 검증의 필요·비용(§10.1)** — 상시 검증 없이 분쟁/어뷰징 샘플 재실행만으로 충분한지, 재실행 인프라(코어의 서버 컴파일) 유지 비용이 정당한지.
12. **WASM 결정론 동등성(§12)** — 웹 확장 시 WASM 타깃이 모바일 AOT와 상태 해시 일치를 보장하는지 조기 스파이크로 확인(부동소수 금지가 지켜졌다는 전제의 실증).
