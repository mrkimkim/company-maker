## 0. 문서의 지위와 의존 전제

### 0.1 지위

본 문서는 게임 "회사 경영 시뮬레이션"의 **접근성·현지화 단일 정본**이다(`README.md` §2.3의 소유권: 접근성·현지화 = 본 문서). 접근성 준수 기준, 접근성 설정 화면 명세, 햅틱 정책, 국제화(i18n) 설계 규칙, 현지화(l10n) 전략·파이프라인·용어집·LQA·규제 대응을 소유한다. 클라이언트 엔지니어·현지화 벤더·QA는 본 문서만으로 접근성 구현 착수와 현지화 발주가 가능해야 한다(README §2.4 Definition of Ready).

**본 문서는 게임 규칙을 만들지 않는다.** 규칙·엔티티·자원·용어의 정본은 `game-design.md`이며, 접근성·현지화는 그 규칙을 **모든 사용자가 접근 가능한 형태로, 모든 언어권에서 동일한 경험으로** 전달하는 계층이다. 어떤 접근성·현지화 결정도 새 자원·처리 단계·의사결정을 신설하지 않는다.

**본 문서는 톤을 만들지 않는다.** 정서·보이스·네이밍의 정본은 `narrative-tone.md`이며, 현지화 톤은 전적으로 그 문서에 종속된다. 충돌 시 `narrative-tone.md`가 우선한다.

# Part A — 접근성 (Accessibility)

## 1. 접근성 원칙·목표 준수 기준

### 1.1 접근성 헌장 (톤 헌장의 접근성 번역)

`narrative-tone.md` §0.3 톤 헌장을 접근성 원칙으로 번역한다. 충돌 시 톤 헌장이 우선한다.

1. **누구도 배제하지 않는다.** 시각·청각·운동·인지 특성과 무관하게 완주까지 도달 가능해야 한다. 접근성은 "잘 보이고 잘 들리는 사용자"를 위한 편의가 아니라 게임의 **진입 필러**다(P3 미드코어의 접근성 있는 진입).
2. **어떤 정보도 단일 채널에 갇히지 않는다.** 색·소리·모션 중 하나만으로 전달되는 게임 정보는 없다 — 항상 대체 채널이 있다(ux 4중 부호 §2.1, audio 리던던시 §4).
3. **소리 없이도 완전한 게임이다.** 무음·무진동 상태에서 모든 판단·조작이 가능하다(audio §5.1 보증의 이행 검증 §4.3).
4. **처벌하지 않는 접근성.** 접근성 보조 기능은 죄책감·긴급·강박을 만들지 않는다(톤 §8). 알림 절제·타이머 압박 완화(§5.3)는 인지 접근성이자 톤 헌장의 이행이다.
5. **존엄을 지키는 표현.** 색맹 모드·큰 텍스트·스크린 리더 사용이 "다른 게임"으로 느껴지지 않게, 접근성 경로도 동일한 따뜻함·완성도를 유지한다.

### 1.2 목표 표준

- **설계 결정: 접근성 목표 표준은 WCAG 2.1 레벨 AA를 모바일 게임 맥락으로 적용하는 것으로 확정한다.** 근거: art §3.5가 이미 AA를 아트 측 최소 기준으로 상속했으므로 전 표현 계층의 단일 기준이 된다. WCAG는 웹 기준이나 대비·색 비의존·텍스트 크기·모션·입력 대체 등 핵심 성공 기준은 모바일 UI에 직접 이식 가능하다. 게임 특유 표면(실시간 시뮬·연출)은 아래 플랫폼 가이드와 게임 접근성 가이드라인으로 보완한다.
- **플랫폼 접근성 가이드 준수(A0):**
  - **iOS** — Apple 접근성 API를 상속·존중: VoiceOver, Dynamic Type, Reduce Motion, Differentiate Without Color, Bold Text, Reduce Transparency, 시스템 무음 스위치, Core Haptics.
  - **Android** — TalkBack, 시스템 글꼴 크기(Font scale), 애니메이션 제거(Remove animations), 색 보정(Color correction)·색 반전, 진동 설정.
- **게임 접근성 참고 프레임:** 업계 통용 게임 접근성 가이드라인(입력·시각·청각·인지 4대 축의 Basic/Intermediate/Advanced 티어)을 체크리스트로 참조하되, 본 게임 범위는 §1.3 우선순위로 스코프한다.
- **설계 결정: 시스템 접근성 플래그를 기본 상속하고, 인앱 설정이 있으면 인앱이 우선(override)한다.** 근거: 시스템 설정을 따르면 기본 접근성이 자동 보장되고(사용자가 기기 전역에서 이미 켠 설정을 다시 켤 필요 없음), 인앱 오버라이드로 게임 단위 미세 조정을 준다. 예: 기기 Reduce Motion이 켜져 있으면 흥행 롤 리빌 연출은 자동으로 저자극 대체(ux §4.6)되며, 인앱에서 별도로 다시 조정 가능.

### 1.3 지원 범위 우선순위 (소규모 팀 현실 반영)

P5(소규모 팀) 하에서 "전부 완벽"은 비현실적이다. 접근성을 **차별화 없이 축소하지 않되, 구현 순서를 티어로 명시**한다.

| 축 | A0 (출시 차단) | A1 (1차 출시 목표) | A2 (확장·후속) |
|---|---|---|---|
| **시각** | 대비 AA(§2.2), 색 비의존 4중 부호(§2.1), 텍스트 크기 3단계+시스템 동적 타입(§2.3), 다크/라이트(§2.5), 모션 감소·플리커 금지(§2.6) | 색맹 프로파일 3종(§2.4), 고대비 모드 | 완전 스크린 리더 커버리지(핵심 플로우는 A1) |
| **운동** | 터치 타깃 최소치(§3.1), 제스처 전면 탭 대체(§3.3), 강한 확인·예약 취소(§3.4) | 한 손 도달 최적화 검증, 확인 방식 선택(홀드↔탭) | 스위치 컨트롤·외부 입력 |
| **청각** | 오디오 리던던시(무음 완전 플레이, §4), 3독립 볼륨+음소거(§7) | 시각 알림 강화, 자막 표준(§4.2 — VO는 post-MVP) | 풀 VO 자막(post-MVP VO 도입 시) |
| **인지** | 튜토리얼리스 온보딩(§5.1), 타이머 압박 없음(§5.3), 재진입 도움(§5.4), 명령 거부 사유 명시 | 텍스트 명료성 검수, 코치마크 재열람 | 읽기 보조(용어 사전 상시), 난이도 옵션 |

- **설계 결정: 완전한 스크린 리더(VoiceOver/TalkBack) 커버리지는 "핵심 플로우 A1 + 전체 A2"로 단계화한다.** 근거: 게임 엔진(Unity/Unreal — `technical-architecture.md` 소관) UI는 네이티브 접근성 트리 자동 노출이 제한적이라, 접근성 라벨·역할·값을 수동 부여해야 한다(P5 비용 큼). 코어 루프(채용→편성→하달→완료→급여, ux §4.2)와 위기 복귀 플로우(ux §4.5)의 인터랙티브 요소부터 라벨링하고, 전 화면 커버리지는 후속 확대. 최소한 무음·색 비의존 리던던시로 스크린 리더 없이도 시각 사용자는 완전 플레이 가능하므로, 스크린 리더는 전맹 사용자 대상의 추가 채널이다.

### 1.4 준수 검증 방식

- **대비 검증:** 스타일 가이드 색 토큰(라이트/다크 쌍, art §11-1)이 확정될 때 자동 대비 검사(4.5:1/3:1)를 CI 게이트로 건다. 업종 틴트 배경 위 텍스트 조합도 검사 매트릭스에 포함(§2.2).
- **색맹 검증:** 1형(적색맹)·2형(녹색맹)·3형(청황)·전색맹 시뮬레이션으로 핵심 화면(스위처·대시보드·보드·직원 카드·결산) 캡처 검수(art §3.5 시나리오).
- **무음 플레이 통과 테스트:** 마스터 볼륨 0 + 햅틱 off로 온보딩~완주 대표 플로우 완주 가능 확인(audio §8.3-5 "무음 플레이 통과 테스트" 연동, §4.3).
- **현지화 회귀:** 각 로케일 빌드에서 잘림·겹침·미번역 키 자동 검출(§10.3).

## 2. 시각 접근성

### 2.1 색 단독 정보 금지 — 4중 부호 계약 구체화

ux §7.1의 계약("모든 위험 신호는 색+아이콘+텍스트+배치의 4중 부호, 색은 보조 채널")을 **신호별 부호 명세**로 확정한다. 색은 4개 채널 중 하나일 뿐이며, 색을 완전히 제거해도 나머지 3채널로 신호가 성립해야 한다.

**공통 규칙:**
- 색은 **의미를 실어 나르는 유일 채널이 될 수 없다** — 언제나 아이콘/형태 + 텍스트 라벨 + 위치가 병기된다.
- 아이콘·형태는 색을 뺀 실루엣만으로 구별되어야 한다(art §7 자원 아이콘 계약과 정합 — "색을 빼도 형태로 구별").
- 증감(±)은 부호(+/−) + 방향 아이콘(↑/↓) + 색으로 표현하며 색 단독 금지(ux §9 마이크로카피).

**신호별 4중 부호 명세(정본):**

| 신호 (ux §7.1) | ① 색(보조) | ② 아이콘/형태 | ③ 텍스트 라벨 | ④ 배치/위치 |
|---|---|---|---|---|
| 재무 상태 **건전** | 안정 그린(art §3.4) | 체크/정상 마크 | "건전" | 스위처 카드·대시보드 신호점 |
| 재무 상태 **주의**(오버레이) | 소프트 앰버 | 옅은 느낌표(주목) | "주의 · 다음 달 빠듯" | 배너 오버레이(어느 상태 위에도) |
| 재무 상태 **부실** | 진한 앰버/오렌지 | 경고 마크 + 보더 패턴 | "부실" | 대시보드 상단 배너 + 큐 위기 티어 |
| 재무 상태 **파산 임박** | 뮤트 레드브라운 | 정리 마크(해골·폭발 금지) | "파산 임박" | 큐 최상단 + 카드 신호점 |
| **이탈 위험**(충성도<임계) | 경고 앰버 | 유대 저하 아이콘 | "이탈 위험" | 직원 카드 배지 + 명부 정렬 상위 |
| **컨디션 저하**(과로) | 앰버 | 에너지 저하(배터리 낮음류) | "과로 · 컨디션 N" | 팀 편성·진행 현황(팀 평균+개인) |
| **팀장 부재/표류** | 중립 저채도 | 빈 캡틴 인시그니아 | "표류 · 팀장 공석" | 팀 카드 라벨 + 진척 0 표시 |
| **장기 저가동** | 중립 | 유휴 마크(zzz류) | "N일 저가동" | 부서 뷰 + 큐 정보 티어 |
| **미지급 예측** | 소프트 앰버 | 예측/시계 마크 | "다음 달 빠듯" | 대시보드·재무·큐 |

- **설계 결정: 파산·부실은 보더/텍스처 패턴을 4번째 부호로 추가한다(색맹·저대비 강건성).** 근거: art §3.4가 위기 스펙트럼을 "그린→앰버→진한 앰버→뮤트 레드브라운"의 단조 온도 상승으로 잡았는데, 색맹 사용자에게 앰버 계열의 미세 온도차는 뭉개진다. 가장 행동이 급한 부실/파산에 패턴(빗금/이중 보더)을 얹어 색 없이도 위계가 읽히게 한다.
- **직원 등급 배지:** C/B/A/S는 항상 **문자를 노출**한다(art §4.3와 정합 — 프레임 색만으로 등급 판단 금지). 색맹 안전 문자 채널이 기본.
- **자율/직접 태그:** 부서 배지는 색이 아니라 아이콘+라벨("자율"/"직접")로 구별(ux §4.3 상시 노출 계약).

### 2.2 명도 대비 기준 (아트 팔레트가 지켜야 할 수치)

art §3.5가 상속을 요청한 씨앗을 **본 문서가 최종 확정**한다. 스타일 가이드의 모든 색 토큰(라이트/다크 쌍)은 아래를 만족해야 하며, §1.4의 CI 대비 게이트가 이를 강제한다.

| 대상 | 최소 대비 | 근거 |
|---|---|---|
| **본문 텍스트**(작은 글자) | **≥ 4.5:1** (배경 대비) | WCAG 2.1 AA 1.4.3 |
| **큰 텍스트**(굵거나 대형, ≥ 약 24px/굵음 ≥ 약 19px) | **≥ 3:1** | WCAG 2.1 AA 1.4.3 |
| **아이콘·상태 경계·의미 있는 도형·UI 컴포넌트 경계** | **≥ 3:1** (인접 색 대비) | WCAG 2.1 AA 1.4.11 |
| **비활성(disabled) 요소** | 대비 기준 예외이나 형태/라벨로 상태 식별 가능해야 함 | 관례 |

- **업종 틴트 배경 제약(핵심):** 게임개발(딥 인디고/네이비, 대비 큼)·무역(웜 중~고채도)·화장품(파스텔 저채도) 등 업종 무드 틴트가 카드 헤더·배경에 적용될 때(art §3.3), **그 위의 텍스트도 4.5:1을 넘도록 배경 명도를 제한**한다. art §3.5가 요구한 "업종 틴트 배경 위 텍스트도 기준을 넘도록 배경 명도를 제한"의 이행이며, 특히 저채도 화장품 파스텔 위 옅은 텍스트와 고대비 게임개발 네온 글로우 위 텍스트가 검사 매트릭스의 주 위험 조합이다.
- **다크/라이트 각각 검증:** 대비는 라이트 팔레트·다크 팔레트에서 **독립적으로** 만족해야 한다(§2.5). 한 쪽만 통과하는 토큰은 불합격.
- **설계 결정: 게임 정보를 전달하는 저채도 배경 요소(패럴랙스 3레이어 오피스 배경, art §5.6)는 대비 기준 예외로 두되, 그 위에 정보 텍스트를 얹지 않는다.** 근거: 배경은 "콘텐츠 뒤 저대비"로 정보 가독성을 방해하지 않게 깔린다는 art §2.3 계약과 정합 — 장식 레이어는 대비 대상이 아니고, 정보는 항상 카드 지면(뉴트럴 서피스) 위에 놓인다.

### 2.3 폰트 스케일·동적 타입

ux §10 "폰트 스케일/다이나믹 타입: 텍스트 확대 시 레이아웃 리플로우(잘림·겹침 금지), KO 기준 +40% 팽창 흡수"를 이행한다.

- **설계 결정: 인앱 텍스트 크기 3단계(기본/크게/아주 크게) + "시스템 글꼴 크기 따르기" 토글을 제공한다.** 근거: 시스템 동적 타입(iOS Dynamic Type / Android Font scale)을 따르면 기기 전역 설정이 자동 반영되고, 인앱 3단계는 시스템을 쓰지 않는 사용자·게임 단위 조정용. 무단계 슬라이더 대신 3단계인 이유: 9-슬라이스 레이아웃(art §6)이 흡수해야 할 조합 폭을 검증 가능한 수준으로 제한.
- **확대 흡수 규격:** 텍스트 컨테이너는 9-슬라이스(art §6)로 세로 확장되며, 확대 시 **잘림·말줄임(…) 없이 리플로우**한다. 현지화 팽창(+40%, §8.4)과 **동일한 여백 예산을 공유**한다 — 한 번의 레이아웃 강건성 확보가 두 요구를 동시에 만족.
- **최소 폰트 크기:** 본문 최소 렌더 크기를 정해(스타일 가이드 토큰) 그 이하로 축소되지 않게 한다. 아이콘 병기 라벨(≤6자, ux §9)도 최소 크기 이하로 내려가지 않는다.
- **가로 스크롤 금지 원칙 유지:** 텍스트 확대로도 페이지 몸통이 가로로 밀리지 않는다(art §2.2). 넓은 콘텐츠(결산 비교표)는 자체 가로 스크롤 컨테이너로 격리.

### 2.4 색맹 모드

- **설계 결정: 색맹 프로파일 3종 + 전색맹(모노)을 제공한다 — 없음 / 적·녹 보정(1형·2형) / 청·황 보정(3형) / 모노크롬.** 근거: art §3.5가 요구한 검증 시나리오(적/녹, 청/황)와 1:1 대응. 색 보정은 게임 전역 색 토큰에 프로파일별 변환을 적용하되, **4중 부호(§2.1)가 이미 색 비의존을 보장하므로 색맹 모드는 "추가 편의"이지 필수 정보 채널이 아니다** — 색맹 모드 없이도 형태·라벨로 완전 플레이 가능.
- **심볼 강화 옵션("색 외 표식 강조"):** 켜면 재무 상태·자율/직접 태그·자원 등에 아이콘/패턴 대비를 한 단계 강화(iOS Differentiate Without Color / Android 상속). 색맹 프로파일과 독립 토글.
- **위기 스펙트럼 강건성:** §2.1 설계 결정(부실/파산 패턴 부호)이 색맹 사용자에게 위기 위계를 색 없이 전달한다.

### 2.5 다크/라이트 모드

- **설계 결정: 라이트/다크 두 테마를 모두 지원하고, 기본은 "시스템 따르기"로 한다.** 근거: art §11-1이 색 토큰을 "라이트/다크 쌍"으로 산출하기로 이미 확정했으므로 아트 자산이 두 테마를 전제한다. 모바일 다크 모드는 배터리(OLED)·야간 눈부심·개인 선호의 접근성 요소이며, 시스템 따르기가 사용자 기대에 부합.
- 설정에서 라이트/다크/시스템 따르기 3택. 두 테마 각각 §2.2 대비 기준을 독립 만족(§1.4 검증).
- 업종 무드 틴트(art §3.3)는 두 테마에서 각각 명도 조정되어 무드 정체성은 유지하되 대비를 깨지 않는다.

### 2.6 모션·플리커·기타 시각 안전

- **모션 감소:** ux §4.6·art §8.7과 정합 — "모션 감소" 설정 시 흥행 롤 리빌·승급·완주 축하·화면 전환 연출을 즉시/저자극 대체로 표시(결과를 지연 없이 표시, 슬롯머신형 연출 제거). 시스템 Reduce Motion 상속 + 인앱 오버라이드.
- **플리커/발작 안전(A0):** 명멸·고대비 플리커·초당 3회 초과 번쩍임 금지(art §3.5 모션 안전). 어떤 축하 연출도 이 한계를 넘지 않는다.
- **투명도 감소:** iOS Reduce Transparency 상속 시 반투명 오버레이(바텀시트·말풍선)를 불투명 대체.
- **명도 위계 유지:** 배경 < 카드 지면 < 텍스트/액션의 명도 계단(art §3.5)으로 시선 순서를 색 없이도 만든다 — 저시력 사용자에게 정보 위계 채널.

## 3. 운동·조작 접근성

### 3.1 터치 타깃 최소 크기

ux §10 "모든 인터랙티브 요소는 최소 터치 타깃 이상"의 수치를 확정한다.

- **설계 결정: 인터랙티브 요소의 최소 터치 타깃 = 48×48 dp(Android) / 44×44 pt(iOS), 요소 간 최소 간격 8 dp.** 근거: 두 플랫폼 가이드의 권장치(iOS HIG 44pt, Android Material 48dp)의 합집합을 최소 기준으로 삼아 양 플랫폼을 동시에 만족. 세로·한 손·짧은 세션(P1)에서 오조작은 세션 완결감을 직접 해친다.
- **시각 크기 < 히트 영역 허용:** 촘촘한 표면(편성 슬롯, 보드 카드, 스위처 10사 리스트)에서 아이콘의 **시각 크기가 작아도 히트 영역은 최소치를 확보**한다(ux §10 "간격·히트영역 확보"). 인접 타깃의 히트 영역이 겹치지 않게 간격 우선.
- **주 액션 배치:** 엄지 우세 도달 구역(하단·중앙)에 주 액션(하달·확정·채용), 상단은 보조 액션만(§3.2).

### 3.2 한 손 조작

ux §10·P1의 한 손·세로 원칙을 이행한다.

- 주 흐름은 하단 탭바(5탭)·바텀시트로 처리하고, 상단 도달이 어려운 요소(설정·상점·메뉴 ⋯)는 보조 액션으로만 배치(ux §2.2·§10).
- 회사 스위처는 상단 좌측 칩이나, 자주 쓰는 활성 전환은 스위처 오버레이(바텀시트)로 내려 엄지 도달 확보(ux §2.3).
- **설계 결정: 좌/우 우세손 모두 고려해, 파괴적 액션(해고·청산 확정 버튼)을 항상 화면 한쪽 모서리에 고정하지 않는다.** 근거: 우세손에 따라 실수 위험 위치가 달라지므로, 강한 확인(§3.4)을 파괴적 액션의 안전장치로 두어 손 우세와 무관하게 오조작을 흡수.

### 3.3 제스처 대체 (모든 제스처에 탭 대안)

ux §10 "모든 제스처(스와이프 스위처, 홀드 확인)에 탭 대체 경로 제공 — 제스처 단독 필수 금지"를 매핑으로 확정한다.

| 제스처 | 기능 | 탭 대체 경로(A0) |
|---|---|---|
| 스와이프 | 회사 스위처 좌우 전환 | 스위처 오버레이의 회사 카드 **탭** 선택 |
| 홀드(길게 누르기) | 청산·해고 등 강한 확인 | "확인" 버튼 **2스텝 탭**(텍스트 확인) — 설정에서 홀드↔탭 선택(§7) |
| 스와이프 | 알림/큐 항목 처리·닫기 | 항목 탭 → 액션 시트 |
| 드래그 | 미배치 풀 → 팀 슬롯 배치 | 슬롯 탭 → 인원 선택 리스트 탭 |
| 핀치/줌 | (사용 시) 확대 | 텍스트 크기 설정(§2.3)으로 대체, 핀치는 필수 아님 |
| OS 뒤로 제스처 | 스택 pop | 상단 좌 back 버튼(ux §2.4) |

- **설계 결정: 드래그 앤 드롭 배치는 항상 "탭-투-선택" 대체를 병행 제공한다.** 근거: 편성(ux §S4)이 미배치 풀 드래그를 주 제스처로 쓰면 운동 제약·소근육 정밀도 낮은 사용자를 배제한다. 슬롯 탭 → 후보 리스트 탭의 2탭 경로가 동일 결과를 낸다.
- 다중 손가락 제스처를 게임 필수 조작으로 쓰지 않는다.

### 3.4 오조작 방지·확인·되돌리기 (예약 명령 연동)

game-design §2.2(모든 지시 = 일 처리 1단계 일괄 반영)·ux §7.2(예약 명령 되돌리기)를 접근성 안전장치로 이행한다.

- **자연 되돌리기 = 예약 커밋 전 취소:** 대부분의 명령은 다음 사이클 1단계에 반영되므로, 현재 사이클 내 "예약됨" 항목을 취소·수정할 수 있다. UI는 "예약됨 · 취소" 스낵바 + 예약 목록을 노출(ux §7.2). 이는 오조작에 대한 기본 방어선이며, 운동·인지 접근성의 핵심 완충이다.
- **강한 확인(2스텝, A0):** 되돌릴 수 없거나 무거운 결과 — **해고·청산·파산 임박 회사의 승급·대량 재배치**(ux §7.2). 확인 방식은 **홀드 제스처 또는 텍스트 확인 중 설정에서 선택**(§3.3·§7). 파괴적 액션의 확인 버튼은 화면상 위치를 긍정 버튼과 분리해 오탭을 줄인다.
- **명령 거부는 침묵하지 않는다(A0):** 자금 부족·총원 상한·불변식 위반으로 지시가 거부되면 리아 보이스로 "무엇이·왜·다음 수"를 반환(ux §7.3). 이유 없는 실패는 인지 접근성 최대 이탈 요인이며, 거부 사유가 곧 학습.
- **설계 결정: 파괴적 액션에 실행 취소 유예를 두지 않는 대신, 확인 전 미리보기를 강화한다.** 근거: game-design §2.2상 명령은 원자적으로 확정되어 반영 후 롤백이 자원 정합을 깬다(ux §7.2 "범용 undo 없음"). 대신 청산은 반환 골드·소멸 목록 미리보기(ux §S15), 해고는 대상·영향 요약을 확인 화면에서 명시해 "확정 전 이해"를 최대화한다.

## 4. 청각 접근성

### 4.1 오디오 리던던시 이행 (audio 계약)

audio §5.1의 핵심 원칙("오디오는 어떤 게임 정보의 유일한 전달 채널이 될 수 없다")을 접근성 측 검증 계약으로 이행한다.

- **모든 사운드 이벤트는 대응 시각 신호를 전제로 존재한다.** audio 발주 티켓의 "대응 시각/햅틱 신호" 필드(audio §5.1·§8.3)가 채워졌는지 접근성 리뷰에서 확인 — 대응 시각 신호가 없는 사운드 이벤트는 리던던시 위반으로 반려.
- **오디오-비주얼-햅틱 동기 계약(audio §5.2):** 같은 사건은 세 채널에서 같은 타임코드로 발화. 본 문서는 햅틱 정책(§6)을 소유하고, 시각은 ux/art 소관이며, 세 채널의 동기 검증을 §4.3 무음 테스트에서 수행.
- **정보 위계별 대체 채널 매핑:**

| 오디오 사건(audio) | 필수 시각 대체(ux/art 소관) | 햅틱(§6, 중요 사건만) |
|---|---|---|
| 흥행 롤 결과 4등급(STG-05~07) | 성과 등급 리빌 화면·등급 라벨·꼬리 스케줄 시각화(ux §S17) | 강도 4단계(히트=강…실패작=미약) |
| 프로젝트 완료/실패(SFX-GP-05/06) | 완료·실패 토스트·진행바 상태 전이(ux §S7) | — |
| 자금/골드 획득·지출(SFX-TX/GD) | 잔액 변동 애니메이션·부호·아이콘(ux §9) | 확정 시 중강도 |
| 알림 3종+미지급 예측(SFX-NT) | 큐 항목·회사 태그 배지(ux §5.1) | 약(가벼운 틱) |
| 리아 사운드 로고(§6.2 audio) | 리아 말풍선·코멘트 텍스트(ux §9) | — |

### 4.2 자막·시각 알림

- **MVP 청각 접근성 = 리던던시 + 텍스트 화자.** MVP는 풀 VO 없이 출시하므로(audio §6.1), 리아·직원·이벤트 텍스트는 **이미 텍스트가 1차 채널**이다 — 전통적 음성 자막이 불필요하며, 청각 사용자 배제 위험이 구조적으로 낮다. 사운드 로고·SFX·음악은 언어 비의존이며 §4.1 시각 대체가 이를 보완.
- **시각 알림 강화(A1):** 앱 내 알림음(노크 계열, audio §3.5)은 항상 큐 항목·배지·회사 태그와 동반. 무음 사용자를 위해 알림의 시각 강도(배지 애니메이션·상단 벨 카운트)가 소리 없이도 개입 필요를 전달.
- **설계 결정: post-MVP에서 VO를 도입하면 자막을 기본 ON으로 제공하고, 화자·핵심 대사를 자막 표준으로 표기한다.** 근거: audio §9.3이 "자막·시각 대체 표현 표준"을 접근성 소관으로 위임했다. VO 도입 시 자막 규격 — (1) 리아 단일 화자 표기, (2) 동적 값(회사명·직원명·금액)은 텍스트로 정확 렌더(audio §6.3 VO 제외 대상과 정합), (3) 자막 크기는 텍스트 크기 설정(§2.3) 연동, (4) VO on/off와 무관하게 텍스트로 완전 플레이 가능(리던던시 유지).

### 4.3 무음 완전 플레이 보장

audio §5.1 보증("소리 없이도 게임이 완전히 플레이 가능")을 **검증 절차로 확정**한다.

- **무음 플레이 통과 테스트(A0):** 마스터 볼륨 0 + 시스템 무음 + 햅틱 off 상태에서 다음을 완주 가능해야 통과:
  - 온보딩 M1~M6(코어 동사 6종), 코어 루프 1사이클(채용→편성→하달→완료→급여), 위기 복귀(부실 인지→복귀 수단), 흥행 롤 결과 인지(등급·꼬리를 소리 없이 시각으로 구별), 청산·설립, 월말 결산 이해.
- **판정 기준:** 각 사건에서 "무슨 일이 일어났는지"와 "다음에 무엇을 할지"가 **시각(필요 시 햅틱)만으로** 판단 가능한가. 하나라도 소리 없이 판단 불가면 리던던시 위반 → 해당 사건에 시각 대체 추가.
- audio §8.3-5의 "무음 플레이 통과 테스트"와 단일 테스트로 통합 운영(중복 방지).

## 5. 인지 접근성

### 5.1 튜토리얼리스 온보딩의 인지 부하 관리

game-design §11.5·ux §8·narrative §6.1(별도 튜토리얼 모드 없음, M1~M6이 튜토리얼)을 인지 접근성으로 이행한다.

- **한 번에 한 개념(A0):** M1~M6 각 걸음은 정확히 하나의 코어 동사를 다룬다(ux §8-1). 인지 부하를 걸음당 1로 유지.
- **점진 공개:** 현재 걸음의 표면만 스포트라이트, 아직 무의미한 표면은 흐림/숨김(ux §8-2). 규칙을 잠그지 않고 시선만 좁혀 선택지 과부하를 방지.
- **개념 재프레이밍:** "등급 = 잠재력"(M1), "자율 = 위임"(M7)을 결정적 순간에 심는다(ux §8-4). 오해 소지 개념을 선제적으로 교정해 인지 마찰을 줄인다.
- **재프레이밍 상시 접근:** 잠재력·`α_auto`(페널티)·상비 의뢰·미지급 이월 등 핵심 용어는 인라인 "?" 툴팁으로 언제든 재확인(ux §9). 온보딩을 놓치거나 잊은 사용자를 위한 안전망.
- **설계 결정: 코치마크는 재열람 가능하게 하고, 스킵해도 마일스톤은 조건으로 자동 흐른다.** 근거: ux §8-5·§4.1 — 인지 특성상 한 번에 이해하지 못하는 사용자를 위해 "다시 보기"를 설정(§7)에 두되, 스킵 사용자를 막지 않는다(마일스톤이 곧 튜토리얼이므로 별도 스킵 상태 불요).

### 5.2 텍스트 명료성

- **단일 화자·일관 어휘:** 모든 텍스트가 리아 보이스로 통일(ux §9)되어 화자 전환에 따른 인지 부하가 없다. 용어는 game-design §4 사전을 정본으로 재사용(README §2.1) — 같은 개념에 다른 표현을 쓰지 않는다.
- **간결·행동 지향:** 길이 예산(§8.4)이 텍스트를 짧게 강제한다. 알림은 "회사 태그 + 상황 + 행동 힌트"의 고정 구조(ux §5.1)로, 무엇을 할지가 항상 명시.
- **숫자 가독:** 대형 수는 로케일별 축약(만/억 ↔ K/M), 자금·골드는 아이콘 병기, 정렬 일관(ux §9). 자릿수 나열보다 축약이 인지 부하가 낮다.
- **명료성 검수(A1):** 현지화 전 KO 원문의 명료성·모호성을 검수해 번역 파생 오류를 원천 차단(§10.2).

### 5.3 속도/타이머 압박 완화 (FOMO 금지와 정합)

game-design §5.6·narrative §8·ux §4.5(위기 화면 FOMO 금지·게임오버 없음)를 인지 접근성으로 이행한다.

- **압박 타이머 없음(A0):** 어떤 화면에도 카운트다운·긴급 과장·"지금 안 하면 큰일" 카피를 두지 않는다(ux §4.5·§9, narrative §8-2·6). 방치는 설계된 플레이이며(P1·game-design §9), "언제 돌아와도 괜찮다"를 톤·UI가 지지.
- **위기 = 안내된 회복:** 부실·파산조차 처벌이 아니라 복귀 체크리스트로 표현(ux §4.5). 시간 압박 없이 4수단을 차분히 안내 — 인지 과부하 상태(위기)에서 오히려 압박을 낮춘다.
- **배속은 선택, 강제 아님:** 전역 "빨리 감기"는 능동 플레이어용 옵션이며(ux §6.4), 느리게 진행하려는 사용자를 벌하지 않는다. 회사별 배속·일시정지는 없으나(game-design §2.1), 사이클 자동 진행이라 "매일 버튼 누르기" 같은 반복 조작 부담이 없다.
- **설계 결정: 흥행 롤 빌드업은 접근성상 "즉시 결과 표시" 대체를 보장한다.** 근거: 게임 유일의 서스펜스(audio §3.4)조차 조작적 지연이 되어선 안 되며(빌드업 1~2초 상한), 모션 감소 설정 시 빌드업을 건너뛰고 결과를 즉시 표시(§2.6·ux §4.6). 서스펜스는 원하는 사용자에게만.

### 5.4 재진입 도움 (귀환)

ux §6.3(재진입 = 요약 후 큐 2스텝)을 인지 접근성으로 이행한다.

- **오프라인 요약 시트:** 재진입 시 경과 일수·그동안의 완료·수익·자율 성과·새 예외 큐를 압축 제시(ux §6.3). 자리를 비운 사이 무슨 일이 있었는지를 한눈에 재구성 — 장기 이탈 후 복귀의 인지 재진입 비용을 낮춘다.
- **나무라지 않음:** 복귀 요약은 손실(자율 실패 등)을 사실로 담담히 전하되 탓하지 않는다(ux §6.3, narrative §8-1). 죄책감 없는 재진입.
- **"오늘 할 일" 큐:** 요약을 닫으면 예외 우선 큐로 착지해 "이제 뭘 할까"를 결정론적으로 제시(ux §6.1). 다음 행동을 스스로 찾는 부담을 제거.
- **깊은 작업 초안 보존:** 편성·설립 등 다단계 작업은 중간 이탈 시 초안 보존(ux §6.2) — 작업 기억 부담 완화.

## 6. 햅틱 (정본)

audio §5.2가 "햅틱 정책·설정"을 본 문서 소관으로 위임했다. audio §5.3의 사용 지점 제안을 **정본으로 확정**한다.

### 6.1 햅틱 정책 (사용 지점 확정)

- **설계 결정: 햅틱은 "감정 봉우리 + 결정 확정 + 중요 알림"에 한정해 절제 사용하고, 고빈도·저중요 이벤트에는 쓰지 않는다.** 근거: audio §5.3과 동일 — 무음 사용자에게 햅틱은 오디오의 주 대체 채널이지만, 남용하면 배터리·촉각 피로·주머니 속 오작동 체감을 낳는다. 절제가 곧 신호 가치를 지킨다.

| 강도 | 사용 지점 | 대응 오디오(audio) | 접근성 역할 |
|---|---|---|---|
| **강(임팩트)** | 히트작, 회사 승급, 완주 | STG-05/04/10 | 무음 사용자에게 대성취를 손끝으로 |
| **중(확정)** | 채용·승급 승인·결제 완료·청산/설립 확정 | SFX-UI-03, 트랜잭션음 | 파괴적/중요 확정의 촉각 피드백 |
| **약(가벼운 틱)** | 중요 알림 3종·부실 진입·주요 토글(자율/수동) | SFX-NT-*, SFX-UI-05 | 무음 시 개입 필요 신호 |
| **없음** | 탭·화면 전환·레벨업·진행 틱·꼬리 소액 | 고빈도 | 촉각 피로 방지 |

- **흥행 롤 등급 촉각 구분(A1):** 흥행 롤 결과는 무음 사용자에게도 **햅틱 강도 4단계**(히트=강 / 성공작=중강 / 평작=약 / 실패작=미약~무진동)로 결과 크기를 전달(audio §5.3). 소리 없이도 손끝으로 등급을 구별 — §4.3 무음 테스트의 흥행 롤 항목을 햅틱이 보강.
- **동기:** 햅틱은 대응 오디오·시각과 같은 타임코드로 발화(audio §5.2 멀티모달 정합).

### 6.2 on/off·강도·접근성 활용

- **햅틱 on/off + 강도(약/표준/강) 슬라이더(A0):** 설정에서 제어(§7). 진동 미지원·비선호 기기, 회의·공공장소 대응.
- **즉시 반영:** 햅틱 설정 변경은 재시작 없이 즉시 반영(audio §9.3 계약).
- **설계 결정: 햅틱을 켠 무음 사용자를 1급 대상으로 삼아, 흥행 롤·위기·확정 등 "소리로 전달되던 결정적 사건"이 햅틱만으로도 변별되게 강도 매핑을 설계한다.** 근거: audio §5.1 리던던시의 완성 — 시각+햅틱 조합이 오디오의 완전 대체가 되어야 청각 장애·무음 재생 사용자가 배제되지 않는다.
- **기기 편차 대응(A2):** Android 진동 하드웨어 편차로 4단계 강도가 뭉개질 수 있어(audio §열린질문 6), 폴백 강도 매핑을 검증한다(§열린 질문).

# Part B — 현지화 (i18n / l10n)

## 8. 국제화(i18n) 설계

### 8.1 문자열 외부화·하드코딩 금지 (데이터 파이프라인 연동)

- **설계 결정: 모든 사용자 노출 문자열은 코드·씬에서 분리해 로케일별 리소스로 외부화한다. 하드코딩된 사용자 문자열은 빌드 게이트에서 차단한다.** 근거: P4 다국어를 전제로 설계하므로(README), 문자열이 코드에 박히면 확장 언어(일/중) 추가가 재작업이 된다. 하드코딩 금지는 규칙이 아니라 파이프라인 강제 사항이며 `technical-architecture.md`(데이터 모델·세이브) 확정 시 리소스 포맷·로더를 정합시킨다(전방 계약).
- **키 규약:** `<표면>.<맥락>.<식별자>` 계층 키(예: `notif.crisis.unpaid`, `onboarding.m1.hire`, `catalog.trade.sourcing.t5`). 키는 로케일 불변, 값만 로케일별.
- **업종 카탈로그 = 데이터 팩(핵심):** game-design §12.8·mechanics-spec §10.6에서 업종은 코드 분기 없는 **데이터 팩**이다. 데이터 팩의 사용자 노출 문자열(`industry_def.표시명`, `catalog[].기능명`, 부서 표시명)도 **동일한 외부화 규약을 따른다** — 즉 카탈로그 데이터는 로직 값(티어·보상 파라미터)과 표시 문자열(로케일별)을 분리해 담는다. 이로써 업종 추가 시 신규 문자열 현지화가 데이터 팩 확장으로 닫힌다(§10.4).
- **하드코딩 금지 대상:** UI 라벨, 리아 대사, 알림, 툴팁, 카탈로그 표시명, 오류·거부 사유, 숫자 단위(만/억), 날짜 포맷 문자열. **비대상(외부화 불필요):** 로케일별 이름 풀(§9.3, 별도 shipping), 재화 글리프(₩/골드/다이아 아이콘 — §8.6).

### 8.2 복수형·성별·어순·변수 삽입

- **설계 결정: 문자열 포맷은 ICU MessageFormat 계열(복수형 plural·선택 select·변수 삽입 지원)을 채택한다.** 근거: 한/영/일/중은 복수형 규칙과 어순이 다르다(영어 plural 2형, CJK plural 없음, 어순 SOV/SVO 상이). 문자열 연결(concatenation)로 문장을 조립하면 어순이 깨지므로, 변수 슬롯이 포함된 완전한 문장 템플릿을 언어별로 둔다.
- **변수 삽입:** 회사명·직원명·금액·일수·회사 태그는 `{변수}` 슬롯으로 삽입하며, **문장을 변수로 쪼개 이어붙이지 않는다**. 예: `"{company}의 팀장 자리가 비었어요"` — 조사·어순이 언어별로 자연스럽게.
- **한국어 조사 처리:** 변수 뒤 조사(은/는, 이/가, 을/를)는 받침 유무에 따라 달라지므로, 조사 자동 선택 로직 또는 조사 비의존 문형("○○ — 팀장 공석")을 우선. 동적 이름(회사·직원)이 조사 앞에 오는 문장은 조사 자동화 대상으로 표시.
- **성별:** narrative는 직원·리아의 성별을 텍스트 성능·서사에 결부하지 않으므로(narrative §5.1 다양성, §3.1 리아 포용성) 문법 성별 분기 부담이 낮다. 단 EN 등에서 3인칭 대명사가 필요한 문장은 성 중립 표현(they/이름 재사용)을 기본으로 해 성별 데이터 의존을 피한다.
- **어순:** 완전 문장 템플릿 원칙으로 SOV(한/일)·SVO(영/중) 차이를 언어별 템플릿이 흡수.

### 8.3 폰트·글리프 커버리지 (한/영/일/중 간체)

- **설계 결정: 폰트는 한글·라틴·일본어 가나/한자·중국어 간체 한자를 커버하는 CJK 통합 폰트 패밀리(또는 로케일별 폰트 세트)를 채택하고, 글리프 누락(두부 □) 0을 출시 게이트로 둔다.** 근거: P4 4개 언어가 CJK+라틴을 모두 요구하며, CJK는 글리프 수가 방대해(수천~수만) 폰트 서브셋·용량 관리가 필수다. 누락 글리프는 즉시 가시적 결함이므로 자동 검출.
- **글리프 커버리지 요구:**
  - `ko`: 한글 음절(현대 한글 전 범위) + 라틴 + 기본 문장부호.
  - `ja`: 히라가나·가타카나 + 상용/인명 한자 + 라틴.
  - `zh-Hans`: 간체 상용 한자(GB 기준 상용 집합) + 라틴.
  - 공통: 재화·수치 기호, 등급 문자 C/B/A/S(라틴, §9.4).
- **폰트 용량 관리:** CJK 폰트는 서브셋(실사용 글리프)으로 축소하되, **동적 생성 문자열(회사명·직원명, §9.3)이 서브셋 밖 글리프를 요구할 수 있으므로** 이름 풀에 쓰이는 글리프 범위를 서브셋에 포함하거나, 이름 풀을 폰트 커버리지에 맞춰 구성한다. 초기 다운로드 크기는 ASO 전환율에 영향(marketing 소관·전방 계약)이므로 폰트를 언어별 다운로드로 분리하는 방안을 `technical-architecture.md`와 협의.
- **가독성:** CJK는 라틴보다 작은 크기에서 획이 뭉개지므로, 최소 폰트 크기(§2.3)를 CJK 기준으로 설정. 세로 소형 표시(P1)에서 CJK 가독을 우선.

### 8.4 세로 화면 텍스트 확장·레이아웃 여유

ux §9·narrative §7.1의 "KO 기준 +40% 팽창 흡수"를 i18n 레이아웃 규격으로 확정한다.

- **길이 예산(정본, KO 기준 — ux §9 / narrative §7.1과 단일 기준):**

| 표면 | KO 상한 | 현지화 여유 | 비고 |
|---|---|---|---|
| 알림·큐 항목 | ≤ 40자, 1행 | +40% 흡수 | 회사 태그+상황+행동 힌트 |
| 버튼·라벨·스탯명 | ≤ 6자 | 아이콘 병기 | 최소 폰트 이하 축소 금지 |
| 프로젝트 플레이버 | ≤ 24자, 1행 | +40% | 기능명 별도 |
| 툴팁 | 1~2문장 | 리플로우 | 용어·규칙 설명 |
| 온보딩 스텝 | 1~2문장 | 리플로우 | 한 걸음 한 개념 |
| 리포트 소감 | 1문장 | 리플로우 | — |
| 마일스톤/완주 | 1~2문장 / 제한 없음 | 리플로우 | 전환점·엔딩 완화 |

- **설계 결정: 레이아웃은 "+40% 팽창"을 최소 흡수 목표로 하되, 언어별 실측 팽창률로 검증한다.** 근거: +40%는 톤 문서의 안전 여백이나 언어별 실제 팽창은 다르다 — 한→영 가변, 영→독일어류 +30%(후순위지만 아키텍처 여유), 한→일 대체로 유사~약간 증가, 한→중 간체 대체로 압축(짧아짐). 독일어류 최장 케이스를 후순위 여유로 남겨 레이아웃 강건성을 확보(9-슬라이스, art §6).
- **버튼·라벨(≤6자)의 CJK↔라틴 비대칭:** 6자 KO 라벨이 EN에서 길어지는 경우 아이콘 병기·약어·툴팁 보완(ux §9 "아이콘 병기 전제"). 라벨은 잘림보다 아이콘+짧은 텍스트를 우선.
- **폰트 스케일 여백 공유:** §2.3 텍스트 확대와 §8.4 현지화 팽창은 **동일한 세로 확장 여백을 공유**한다 — 두 요구를 한 번의 레이아웃 강건성으로 만족.

### 8.5 RTL 대비 여부 결정

- **설계 결정: 1차·확장 로드맵 언어(한/영/일/중)는 전부 LTR이므로 완전한 RTL 미러링은 런치·확장 범위 밖(A2 이후)으로 둔다. 단, 아키텍처는 방향 비의존(logical start/end) 레이아웃을 권장해 미래 RTL 비용을 낮춘다.** 근거: RTL(아랍어·히브리어)은 로드맵에 없으므로 지금 미러링을 구현하는 것은 P5 자원의 과투자다. 그러나 하드코딩된 left/right 대신 leading/trailing(start/end) 레이아웃 속성을 쓰면, 후일 RTL 시장 진입 시 재작업이 최소화된다 — 저비용 미래 대비. 완전 RTL(아이콘 미러링·읽기 방향·숫자 처리)은 해당 언어 채택 결정 시 별도 스코프.

### 8.6 날짜·숫자·통화 표기 (재화 표기 현지화 정책)

- **날짜·시간:** 게임 내 시간은 "일(Day)/월(Month=30일)"의 게임 달력이며(game-design §2.1) 실제 캘린더 날짜가 아니다. UI에 실제 날짜가 필요한 경우(세이브 시각·오퍼 기한 등, monetization 소관)만 로케일 날짜·시간 포맷을 따른다. 게임 내 "D-일"·"N개월"은 로케일별 단위 표기(일/day, 월/month/月)로 현지화.
- **숫자:** 천단위 구분자·소수점·자릿수 그룹은 로케일 규칙을 따른다. 대형 수 축약은 로케일별 관용을 따른다 — `ko`: 만/억, `ja`: 万/億, `zh-Hans`: 万/亿, `en`: K/M/B(ux §9 "만/억 ↔ K/M"). 축약 단위는 문자열 외부화 대상(§8.1).
- **설계 결정: 게임 내 재화 기호(자금·골드·다이아)는 실존 통화가 아니라 게임 고유 화폐이므로 번역·환율 변환 대상이 아니며, 전 로케일 공통으로 전용 아이콘을 1차 노출한다.** 근거: 세계는 무국적 가상 세계이고 실존 국가·통화를 쓰지 않는다(narrative §2.1). game-design이 자금을 `₩`로 약기하나 이는 실제 원화가 아니라 게임 화폐 글리프이며, art §3.6·§7.1이 자원별 전용 아이콘을 정의했으므로 **아이콘을 1차 채널로, 텍스트 기호(₩ 등)는 폴백으로** 둔다. 이로써 (1) 무국적 원칙과 정합, (2) CJK 로케일에서 통화 기호 혼동 방지, (3) 색맹 안전(형태 우선, §2.1)을 동시에 만족. 재화 **수량**(숫자)은 로케일 숫자 규칙·축약을 따르되 **기호**는 공통.
- **실화폐(IAP) 가격:** 인앱 결제의 실화폐 표기·현지 가격은 스토어(App Store/Google Play)가 로케일·지역별로 자동 현지화하며, 게임은 스토어 제공 현지화 가격 문자열을 그대로 노출한다(정본은 `monetization.md` — 전방 계약). 게임 내 재화(₩/골드/다이아)와 스토어 실화폐를 표기상 명확히 구분.

## 9. 현지화(l10n) 톤·전략

### 9.1 톤 유지 원칙 (narrative 상속)

narrative §7.2를 현지화 실행 규칙으로 이행한다. 충돌 시 narrative가 우선.

- **불변(반드시 유지):** 다정함, 냉소 없음, 죄책감 없음, 직원 존엄, 낙관. **이 정서가 문장 구조보다 우선한다**(narrative §7.2). 번역이 원문 구조에 충실해도 이 정서를 잃으면 오역으로 간주.
- **기능 문자열은 직역:** 알림·버튼·스탯·숫자·거부 사유는 정확·간결하게 직역(모호성 0 우선).
- **유머·플레이버는 적응 번역(transcreation) 허용:** 말장난·플레이버 한 줄은 직역이 아니라 "같은 미소를 주는 현지 표현"으로 재창작(narrative §7.2). 원문 뉘앙스 노트를 현지화 키트에 첨부(§10.1).

### 9.2 리아 보이스의 언어별 재현

- **단일 화자 통일 유지:** 전 로케일에서 리아가 유일 화자(narrative §3.1). 언어별로 화자가 흩어지지 않게 스타일 가이드(리아 보이스 시트)를 로케일마다 작성.
- **존댓말·격식의 언어별 매핑:** 리아의 "정중하되 친근한" 결을 각 언어의 격식 체계로 옮긴다(narrative §7.2).
  - `en`: 정중하지만 딱딱하지 않은 조력자 톤(과도한 격식·비속 모두 지양).
  - `ja`: 정중체(です・ます)를 기본으로 하되 친근함 유지 — 과공손(敬語 과다)으로 거리감이 생기지 않게.
  - `zh-Hans`: 정중하고 따뜻한 조력자 어투, 딱딱한 공문체 지양.
- **호칭 매핑:** 대표님 → (그룹 도달 후) 회장님(narrative §1.2)을 각 언어의 자연스러운 경영자 호칭으로 — `en`: Chief/Boss → Chairman 계열, `ja`/`zh-Hans`: 사장·대표 → 회장 계열. 호칭 승격이 정체성 진화(창업가→총수)를 표현하므로 승격 단계가 언어별로도 체감되게 매핑.
- **감정 변주 정합:** 좋은 달/나쁜 달의 톤 변화(narrative §6.5)와 리아 사운드 로고 감정 변주(audio §6.2)가 텍스트 톤과 어긋나지 않게 로케일 검수.
- **VO(post-MVP) 정합:** 후일 VO 도입 시 로케일별 성우가 리아 캐릭터·존댓말 톤을 유지(audio §6.3) — 캐스팅은 캐릭터 정합 트랙(narrative §열린질문 1)과 단일 관리.

### 9.3 로케일별 이름 풀 (음역 금지 구현)

narrative §5.1의 설계 결정("이름은 음역이 아니라 로케일별 자연 이름 풀에서 생성")을 구현 규격으로 확정한다.

- **설계 결정: 각 로케일이 성/이름 풀을 독립적으로 shipping하며, 직원·회사 이름은 활성 로케일의 풀에서 생성한다. 로케일 전환 시에도 기존 직원 이름은 고정(엔티티 항상성)한다.** 근거: 한국어 사용자는 "김서준", 영어 사용자는 "Ethan Park"을 보는 것이 몰입에 맞고, 음역("Kim Seojun"을 영어판에)은 어느 쪽에도 자연스럽지 않다(narrative §5.1). 이름은 §8.1 문자열 외부화의 예외로, 로케일별 이름 데이터셋으로 별도 관리.
  - **엔티티 항상성 처리:** 직원 엔티티는 결정론적 시드(mechanics-spec §3, art §4.4 조합형 아바타 시드)로 생성되므로, 이름도 "생성 시점 로케일의 풀 + 시드"로 확정해 엔티티에 저장한다. 이후 로케일을 바꿔도 이미 생성된 직원의 이름·얼굴은 유지(같은 직원 = 같은 이름/얼굴, art §4.4와 정합). 즉 이름은 생성 시 1회 로케일 풀에서 뽑아 상태에 굳힌다.
- **다양성 요구:** 성별·연령 인상이 고르게 분포하도록 풀 구성, 특정 배경 쏠림 금지(narrative §5.1·§3.3). 로케일당 다양성 검수 프로세스(§10.2)를 거친다.
- **성능 비유추:** 등급·직무는 이름에 영향을 주지 않는다(이름으로 성능 유추 금지 — 등급 배지가 정보 채널, narrative §5.1).
- **풀 규모(A1):** 로케일당 성/이름 개수·중복 체감 방지선은 밸런싱·플레이테스트로 확정(narrative §열린질문 5와 단일 트랙, §열린 질문). 최소 규모는 최대 10사×수십 명 동시 보유에서 이름 중복 체감이 몰입을 해치지 않는 수준.
- **회사명 추천 생성기:** 회사명은 플레이어가 짓되 업종별 톤의 자동 추천을 제공(narrative §5.2). 추천 패턴·예시(한길상사/Meridian Trading 등)도 **로케일별 생성 규칙·풀로 shipping**한다 — 로케일마다 자연스러운 업종 향 이름이 추천되게.

### 9.4 용어집(Glossary) 골격과 번역 일관성

- **설계 결정: game-design §4 용어 사전을 정본으로 하는 현지화 용어집(termbase)을 구축하고, 핵심 용어는 로케일별 확정 번역을 고정해 전 문자열에서 일관 사용을 강제한다.** 근거: 시스템 중심 게임에서 같은 개념이 화면마다 다르게 번역되면 학습 전이가 깨진다(README §2.1 "새 용어를 만들지 말고 재사용"의 현지화 이행). 용어집은 번역 벤더·LQA의 단일 참조.

### 9.5 유머·플레이버의 지역 리스크 관리

narrative §7.3을 현지화 리스크 프로세스로 이행한다.

- **한국어 종속 표현 금지:** 한국어에서만 통하는 말장난·유행어·연예/방송 밈은 원문에 넣지 않는다(narrative §7.3). 이미 톤 정본이 이를 금지하므로 리스크가 원문 단계에서 낮다.
- **문화 종속 레퍼런스 부재:** 실존 국가·브랜드·인물·정치·명절·시사를 세계관이 구조적으로 배제(무국적, narrative §2.1) — 정치·역사 민감 소재가 없어 확장 언어권(일/중) 리스크가 근본적으로 낮다.
- **보편 상황 코미디로 승부:** "밤샘한 개발팀", "첫 히트에 얼떨떨한 신입", "빠듯한 월말" 등 어디서나 통하는 워크플레이스 정서에 유머를 싣는다(narrative §7.3) — transcreation이 쉬운 소재.
- **확장 언어권 사전 점검(A1):** 업종·직무·유통 채널 표현 중 지역 상업 관행 차이로 오해될 소지(특정 계약 관행·유통 명칭)를 현지화 리뷰에서 확인(narrative §7.3). 예: 화장품 "드럭스토어/홈쇼핑", 무역 "국제 입찰" 등이 각 시장에서 자연스럽게 읽히는지.
- **뉘앙스 노트 첨부:** transcreation 대상 플레이버는 원문 의도·금지선을 노트로 현지화 키트에 첨부(§10.1) — 번역가가 "같은 미소"를 재현하되 금지선(냉소·비하)을 넘지 않게.

## 10. 번역 파이프라인 · LQA

### 10.1 문자열 관리 (키·컨텍스트·스크린샷)

- **설계 결정: 문자열은 로케일라이제이션 관리 시스템(TMS/스프레드시트+TM)으로 키 단위 관리하며, 각 키에 (컨텍스트 노트 + 표면/화면 + 길이 예산 + 스크린샷/모형)을 제공한다.** 근거: 시스템 중심 게임은 문맥 없는 짧은 문자열(≤6자 라벨 등)이 많아 컨텍스트 없이는 오역이 필연이다. "확정"이 승급 승인인지 채용 확정인지, 화자·상황·길이 상한을 노트로 제공해야 번역 품질이 나온다.
- **키별 메타데이터:** 키 / 표면(ux 화면 코드 S0~S21) / 화자(리아 여부) / 길이 예산(§8.4) / 변수 슬롯 정의 / transcreation 허용 여부(기능=직역, 플레이버=적응) / 뉘앙스 노트 / 스크린샷 참조.
- **번역 메모리·termbase:** §9.4 용어집을 termbase로 연결해 용어 일관성 자동 검사.

### 10.2 번역 → 검수 → LQA 플로우

```
  → [편집 검수(2차 언어 전문가): 용어집·톤 정합·정확성]
  → [인게임 LQA(실빌드): 잘림·겹침·문맥 오류·톤·문화 리스크(§9.5)]
  → [수정 회귀 → 사인오프]
```

- **번역 단계:** 로케일별 번역가는 termbase(§9.4)·컨텍스트·뉘앙스 노트로 작업. 기능/플레이버 구분을 키 메타데이터로 인지.
- **편집 검수:** 2차 언어 전문가가 용어 일관성·톤 불변(다정·비냉소·존엄·낙관, §9.1)·정확성 검수.
- **인게임 LQA(핵심):** 스프레드시트가 아니라 **실제 빌드에서 문맥·레이아웃 검수**. 검출 대상 — 잘림/겹침/줄바꿈 오류, 문맥 오역(같은 키가 두 상황에 쓰이는 경우), 톤 이탈, 문화 리스크(§9.5), 미번역(폴백 노출), 변수 삽입 오류(조사·어순).
- **다양성 검수:** 이름 풀(§9.3)의 성별·연령·배경 분포와 쏠림 여부를 로케일별로 검수(narrative §5.1).

### 10.3 길이 예산 검증 (ux 길이 예산 연동)

- **설계 결정: 각 로케일 빌드에서 §8.4 길이 예산 초과·잘림을 자동 검출하는 회귀를 CI에 건다.** 근거: ux §9/narrative §7.1의 길이 예산은 KO 기준이며, 번역 팽창이 이를 넘으면 세로 화면에서 읽히지 않는다(P1). 수동 LQA만으로는 전 문자열×4언어 커버가 불가하므로 자동 검출로 1차 필터.
- **검출 규칙:** 렌더 후 텍스트 박스 오버플로우·말줄임(…) 발생 키를 플래그 → 번역 단축 또는 레이아웃(9-슬라이스 여백) 조정. 특히 알림(≤40자·1행)·버튼(≤6자)·플레이버(≤24자·1행)의 1행 상한 위반을 우선 검출.
- **폰트 스케일 교차 검증:** 최대 텍스트 크기(§2.3) × 최장 로케일(§8.4 독일어류 여유) 조합에서 잘림이 없는지 교차 검증 — 접근성과 현지화 여백이 같은 레이아웃을 공유하므로 한 회귀로 검사.

### 10.4 업종 추가(§12.8) 시 신규 문자열 현지화 프로세스

game-design §12.8·mechanics-spec §10.6(업종 = 데이터 팩)에 대응하는 현지화 확장 계약.

- **설계 결정: 업종 추가 = 데이터 팩 추가이며, 현지화 관점에서 "신규 로케일 문자열 세트 1벌 + 이름/회사명 추천 규칙 갱신(필요 시)"로 닫혀야 한다. 코어 문자열·파이프라인 구조 변경을 요구하지 않는다.** 근거: game-design §12.8이 업종 추가를 시스템 규칙 불변의 데이터 확장으로 규정했고, narrative §열린질문 8·art §9.5·audio §8.4가 각각 무드 표·아트 팩·L2 레이어 1행 추가로 확장 계약을 정형화한 것과 병렬. 현지화도 데이터 팩 문자열로만 닫혀야 유지보수가 성립.
- **신규 업종 1종이 제공해야 하는 현지화 산출물(계약 체크리스트):**

| # | 항목 | 내용 |
|---|---|---|
| 1 | 업종 표시명 | `industry_def.표시명`의 전 로케일 번역(§8.1) |
| 2 | 부서 표시명 3종 | 공통 영업부 재사용(용어집 기존 값), 신규 고유 부서 2종의 로케일 번역 |
| 3 | 카탈로그 기능명 | `catalog[].기능명` 전 항목의 로케일 번역(직역 원칙) |
| 4 | 프로젝트 플레이버 | 부서·티어별 플레이버 한 줄(≤24자, transcreation, §5.3 narrative) |
| 5 | 용어집 증분 | 신규 고유 용어(예: 신 메커닉 명칭)의 termbase 등재 |
| 6 | 이름/회사명 추천 | 업종 향이 필요한 경우 로케일별 회사명 추천 패턴 갱신(§9.3) |
| 7 | 문화 리스크 리뷰 | 신규 업종의 지역 상업 관행 오해 소지 점검(§9.5) |

- **완주 비소급 정합:** 신규 업종은 기존 완주 판정에 소급되지 않으므로(game-design §11.2·§12.8), 완주 관련 문자열(완주 엔딩·리포트)은 신규 업종 추가로 재작성 불요 — 신규 업종 그룹 달성은 별도 기록 문자열만 추가.

## 11. 문화적 적합성 · 규제

### 11.1 지역별 콘텐츠 리스크

- **구조적 저리스크:** 무국적 세계관이 실존 국가·브랜드·인물·정치·종교·이념·차별을 배제하므로(narrative §2.1·§3.3), 문화·정치 민감 콘텐츠 리스크가 근본적으로 낮다. 이는 확장 언어권(일/중) 진입의 최대 완충.
- **잔여 점검 지점(A1):** (1) 업종·유통 채널 표현의 지역 관행 차이(§9.5), (2) 색·아이콘의 지역 함의(예: 특정 색·제스처 아이콘이 지역에서 다른 의미), (3) 이름 풀의 지역 적절성·쏠림(§9.3·§10.2), (4) 유머 톤의 지역 수용도(narrative §열린질문 3 유머 캘리브레이션과 연동).
- **금지선 재확인:** narrative §3.3 콘텐츠 금지선(차별·선정·정치·풍자·실존 레퍼런스)이 전 로케일 원문·transcreation에 적용됨을 LQA에서 확인.

### 11.2 연령 등급 (결제·규제 연동)

- **전방 계약:** 연령 등급·결제 규제의 최종 정본은 `monetization.md`(결제·재화)이며(README, 미작성), 본 절은 접근성·현지화 측 요구와 등급 심사 입력을 제시한다.
- **등급 심사 입력:** F2P + IAP(다이아, README P2) + 직원 등급 채용(가챠 인접, README P1)이 연령 등급·확률 공시의 주 심사 대상. 콘텐츠 자체는 폭력·선정·도박 묘사가 없어(narrative §3.3) 낮은 연령 등급을 지향할 수 있으나, **결제·확률형 요소가 등급·규제의 실질 트리거**다.
- **지역별 등급·규제 트랙(개요, 정본은 monetization):**
  - **글로벌:** IARC 설문 기반 자체 등급(Google Play 등), App Store 자체 등급 — F2P·IAP 명시.
  - **한국:** 게임물 자체등급분류 + **확률형 아이템 확률 정보 공시 의무**(직원 등급 채용 풀 확률·상점 확률 표시가 대상이 될 수 있음 — game-design의 지원자 풀 등급 분포·명성 연동을 확률 공시 관점에서 monetization·규제와 정합).
  - **일본:** 가챠 관련 자율규제(컴플리트 가챠 금지 등) 준수 확인 — 채용·상점 설계가 저촉되지 않는지 점검.
  - **중국 간체:** 아래 §12에서 상술 — 간체 지원과 중국 본토 직접 서비스는 규제 트랙이 다르다(판호·실명제·미성년 이용 시간 제한).
- **설계 결정: 확률·수량이 개입하는 표면(채용 지원자 풀 등급 분포, 상점 확률형 상품)은 지역 확률 공시 의무를 충족하도록 확률 정보를 현지화된 문구로 노출할 준비를 한다.** 근거: game-design의 채용은 등급 분포가 명성에 연동되는 확률 요소이며, 한국·일부 지역의 확률 공시 규제 대상이 될 수 있다. 공시 문구는 로케일별로 번역·법적 검토 대상(§11.3과 함께).

### 11.3 개인정보·동의 문구 현지화

- **전방 계약:** 개인정보 처리·동의의 법적 정본은 `technical-architecture.md`(세이브·계정·SDK)·`monetization.md`(결제·광고 SDK)·법무이며, 본 절은 **동의 문구의 현지화·접근성 요구**를 소유한다.
- **동의 문구 현지화(A0):** 개인정보 처리방침·이용약관·데이터 동의·(리워드 광고 옵트인 시) 광고 동의 문구는 전 출시 로케일로 번역하며, **법적 정확성이 톤보다 우선**(기능 문자열 직역 원칙의 강한 형태, §9.1). 리아 보이스를 입히지 않는다(법적 고지는 중립 문체).
- **지역 규제 정합:** GDPR(EU, 향후 확장 시)·한국 개인정보보호법·아동 관련(연령 게이트) 등 지역별 동의 요건에 맞춘 문구·플로우. 아동 데이터(COPPA류)는 연령 등급·타깃(§11.2)과 연동해 monetization·법무와 확정.
- **접근성 준수:** 동의 화면도 §2(대비·텍스트 크기)·§3(터치 타깃)·§5(명료성)를 준수 — 동의는 이해 가능해야 유효하다. 필수 동의와 선택 동의를 명확히 구분(다크패턴 금지, narrative §8·P2 정합).
- **설정 내 관리:** 동의·개인정보 관리 진입을 설정(§7)에 상시 배치 — 사용자가 언제든 열람·철회 가능.

## 12. 출시 언어 로드맵

README P4(한/영 1차, 일/중 간체 확장)를 우선순위·트리거로 확정한다. 트리거의 사업·일정 정본은 `production-qa-risk.md`·`marketing.md`(미작성, 전방 계약)이며, 본 절은 현지화 준비의 언어별 스코프·선행 조건을 정의한다.

| 단계 | 로케일 | 스코프 | 트리거 |
|---|---|---|---|
| **1차 (런치)** | `ko`, `en` | 전 문자열 완전 현지화, 이름/회사명 풀, 용어집 확정, LQA 사인오프 | 글로벌 런치(README P5 파이프라인의 소프트런치→글로벌 런치) |
| **확장 A** | `ja` | 전 문자열 + 일본어 이름/회사명 풀 + 가챠 자율규제 점검(§11.2) + 로케일 톤 시트(§9.2) | 1차 런치 안정화 + 일본 시장 지표(marketing 소관) |
| **확장 B** | `zh-Hans` | 전 문자열 + 간체 이름/회사명 풀 + 배포 전략별 규제 트랙 분기(아래) | 확장 A 검증 + 중화권 배포 결정(marketing·법무) |
| **후속(로드맵 밖)** | 기타(독일어류·RTL 등) | 아키텍처 여유만 확보(§8.4·§8.5), 실착수는 시장 결정 시 | 시장 기회 |

- **설계 결정: 확장 언어는 "직전 언어 안정화 + 시장 지표"의 두 트리거를 동시에 만족할 때 착수하며, 언어 추가가 아키텍처·파이프라인 변경을 요구하지 않는다(문자열 세트 + 이름 풀 + 폰트 글리프 + 톤 시트의 데이터 확장으로 닫힌다).** 근거: P5 소규모 팀은 동시 다언어 유지가 부담이므로 순차 확장이 현실적이고, i18n 설계(§8)가 하드코딩 금지·외부화·글리프 커버리지를 이미 확보했으므로 언어 추가가 데이터 작업으로 닫힌다. 이는 업종 확장(§10.4)과 동일한 "데이터 팩 확장" 철학.
- **설계 결정: 중국어 간체 지원과 중국 본토 직접 서비스는 별개의 규제 트랙으로 분리한다.** 근거: `zh-Hans` 지원은 글로벌 스토어의 중화권·해외 중국어 사용자에게 간체 UI를 제공하는 것이며, **중국 본토 앱 배포는 판호(게임 출판 허가)·실명 인증·미성년 이용 시간 제한 등 별도 규제 준수가 선행**되어야 하는 고비용 트랙이다(P5 소규모 팀에 큰 진입 장벽). 간체 현지화는 확장 B에서 언어로서 준비하되, 본토 직접 서비스 여부는 marketing·법무의 별도 사업 결정으로 분리해 언어 확장이 규제 리스크에 묶이지 않게 한다.
- **런치 전 준비 순서:** i18n 인프라(외부화·ICU·폰트 커버리지 §8) → 1차 언어(ko/en) 문자열·이름 풀·용어집 → LQA 회귀 자동화(§10.3) → 확장 언어 순차. i18n 인프라는 1차 런치 전에 완성되어야 확장이 데이터 작업으로 닫힌다.

## 열린 질문

접근성·현지화 정본으로 구조는 확정하되, 프로덕션·플레이테스트·벤더 협업 단계에서 답할 미결 사항.

1. **스크린 리더 커버리지 범위** — 엔진(Unity/Unreal, technical 소관) UI의 접근성 트리 자동화 한계 하에서, 핵심 플로우(A1) 라벨링의 실제 비용과 전체 커버리지(A2) 착수 시점(§1.3).
2. **터치 타깃 최소치의 촘촘한 표면 검증** — 48dp/44pt 최소치가 편성 슬롯·10사 스위처·보드 카드에서 세로 화면 밀도와 충돌하지 않는지(§3.1), 히트 영역 확장으로 충분한지 플레이테스트.
3. **텍스트 크기 3단계의 최대 확대율** — "아주 크게"가 흡수해야 할 팽창 상한과 §8.4 현지화 최장 로케일의 곱집합에서 레이아웃 강건성(§2.3·§10.3).
4. **색맹 프로파일 vs 4중 부호의 실효 검증** — 4중 부호(§2.1)만으로 색맹 사용자가 위기 위계를 충분히 읽는지, 색맹 모드(§2.4)가 필수인지 편의인지 플레이테스트(art §3.5 시뮬레이션 연동).
5. **햅틱 4단계 강도의 기기 편차** — 흥행 롤 등급의 촉각 변별(§6.1)이 Android 진동 하드웨어 편차에서 뭉개지지 않는지, 폴백 매핑 필요 여부(audio §열린질문 6 단일 트랙).
6. **로케일 이름 풀 규모·다양성 기준** — 로케일당 성/이름 개수, 중복 체감 방지선, 다양성 검수 프로세스(§9.3, narrative §열린질문 5 단일 트랙).
7. **리아 존댓말의 언어별 격식 캘리브레이션** — ja/zh-Hans에서 "정중하되 친근"(§9.2)의 실제 격식 수위, 과공손·과친근의 경계(narrative §7.2·§열린질문 1 VO 캐스팅 연동).
8. **확률 공시 규제의 적용 범위** — 채용 지원자 풀 등급 분포(명성 연동)가 한국·지역 확률형 아이템 공시 의무 대상인지, 상점 확률 상품과 함께 monetization·법무 확정(§11.2).
9. **중국 간체 배포 전략** — `zh-Hans` 언어 지원의 실제 타깃(글로벌 중화권 vs 본토), 본토 시 판호·규제 트랙 착수 여부(§12, marketing·법무 결정).
10. **CJK 폰트 용량과 초기 다운로드** — CJK 글리프 서브셋 + 이름 풀 글리프 범위의 폰트 용량이 초기 다운로드 크기(ASO 전환율, marketing)·저사양 메모리(technical)와 정합하는지(§8.3).
11. **transcreation 물량과 반복 체감** — 플레이버(성격 디스크립터·프로젝트 플레이버) transcreation 물량과 로케일별 반복 피로, "조용한 달" 규칙(ux §9)의 현지화 정합(narrative §열린질문 4·9 연동).
12. **동적 타입·현지화 팽창의 공유 여백 실측** — §2.3·§8.4가 공유하는 세로 확장 여백이 실제 언어별 팽창률·폰트 크기 조합에서 충분한지, 독일어류 후순위 여유의 실제 상한(§8.4).
