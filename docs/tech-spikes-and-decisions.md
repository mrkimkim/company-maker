## 0. 개요

### 0.1 목적

M1 프리프로덕션의 4개 기술 게이트(`[DL D-102~105]`)는 서로 다른 시점에 개발을 막는다:

| ID | 결정 | 막는 것(크리티컬 패스) | 동결 시점 | roadmap |
|---|---|---|---|---|
| D-102 | 엔진·코어 언어 | 표현 계층(L2) 착수 | 알파 전 (가역) | M1.2.1 |
| D-103 | 해시 PRNG·믹싱 상수 | 결정론 코어·세이브 | **프로토타입 착수 / 런치 전 동결** | M1.2.2 |
| D-104 | 고정소수 스케일 `FP` | 세이브·밸런스 정밀도 | **프로토타입 / 런치 전 동결** | M1.2.3 |
| D-105 | 세이브 직렬화 포맷 | 세이브·마이그레이션 픽스처 | 알파 전 (동결 성격) | M1.2.4 |

이 문서는 각 게이트에 대해 "무엇을 재고 어떻게 측정하면 결정이 서는가"를 제공해, 팀이 **논쟁이 아니라 측정으로** 게이트를 통과하게 한다.

### 0.2 공통 평가 원칙

4개 결정 모두 아래 원칙을 공유한다. 후보가 이 중 **결정론 보존·바이트 재현성**을 만족하지 못하면 성능·편의와 무관하게 탈락한다(우선순위 하드 게이트).

| # | 원칙 | 의미 | 근거 |
|---|---|---|---|
| C1 | **결정론 보존** | `(스냅샷, 명령 로그) → 후속 상태`의 순수성을 깨지 않을 것. 부동소수·벽시계·비결정 컨테이너 유입 금지 | `[MS §1.1 불변식 D]`, `[TA §0.2]` |
| C2 | **바이트 재현성** | 같은 상태 → 같은 바이트(골든 상태 해시). 크로스플랫폼 동일 출력 | `[TA §2.4, §11]` |
| C3 | **모바일 성능** | 저사양(출시 3~4년 전 보급형)에서 사이클/캐치업 예산 내 | `[TA §9]` |
| C4 | **소규모 팀 유지보수** | P5(인디~부티크) 단일 툴체인·낮은 학습곡선·자동 검증 가능 | `[README P5]` |
| C5 | **크로스플랫폼** | iOS/Android 우선, PC/웹(WASM) 여지. 플랫폼 간 산술·바이트 동일 | `[README P1]`, `[TA §12]` |
| C6 | **되돌릴 수 있는 선택 선호** | 격리·인터페이스·핀으로 오결정의 비용을 낮춘 후보 우대 | `[TA §0.2 L1 분리]` |

- **C6의 비대칭성(중요):** 네 결정은 "되돌릴 수 있는 정도"가 다르다. **D-102(엔진)** 는 L1 코어를 순수 C#로 격리하면 **가역**(표현·서비스만 재작성). 반면 **D-103·D-104·D-105** 는 **한 번 세이브를 만들어 배포하면 준-비가역**이다 — 아래 §0.3.

### 0.3 "런치 전 동결"과 왜 교체가 리플레이 비호환을 일으키는가

`[MS §3.4]`: 세이브에 보관하는 RNG 상태 = `master_seed`(불변) + `day`뿐이고, **모든 롤은 `(seed, stream, 좌표)`의 순수 함수**다. `[MS §7]`: `δ(n)=δ_min+(FP−δ_min)·ζ^n`, `XP_need=X0·ψ^(Lv−1)`, 훈련비 `τ0·φ_train^s` 같은 **복리형 곱**과 모든 진척·품질·보상 산술이 `FP` 스케일 위에서 계산된다. `[TA §2.4]`: 세이브는 정준 순서로 방출된 이진 바이트열이다.

따라서:

- **해시 PRNG 상수(D-103)를 바꾸면** — 같은 `(seed, 좌표)`가 다른 64비트를 낸다 → 지원자·흥행·퇴사·진척 소변동·보드가 전부 달라진다 → **기존 세이브의 리플레이가 재현되지 않는다.**
- **`FP` 스케일(D-104)을 바꾸면** — 저장된 고정소수 값의 의미(`값 = 실수 × FP`)가 달라지고 복리형 곱의 반올림 궤적이 달라진다 → 마이그레이션 없이는 밸런스 결과가 어긋난다.
- **세이브 포맷(D-105)을 바꾸면** — 바이트 레이아웃이 달라져 골든 픽스처·마이그레이션 체인이 깨진다.

> **동결 규칙.** D-103·D-104는 **프로토타입에서 후보를 확정하고 런치 전에 동결**한다. 동결 후의 변경은 "밸런스 핫픽스"가 아니라 **콘텐츠/세이브 버전 경계 = 명시적 마이그레이션 이벤트**로만 허용된다(`[TA §3.3, §7.3]`, `[DL D-111]` 연동). D-105는 포맷 자체를 동결하되 **`save_schema_version` 단조 마이그레이션 체인**으로 진화를 흡수한다(`[TA §3.3]`).

- **동결 = 골든 고정.** 각 결정의 동결은 "문서에 적었다"가 아니라 **골든 테스트 벡터를 커밋했다**로 정의한다(→ §5.4). 이것이 회귀를 상시 차단한다.

## 1. D-102 — 엔진·코어 언어 선정

> **막는 것:** 표현 계층(L2) 착수. **오너:** ENG. **성격:** L1 코어를 순수 C#로 격리하면 **가역 결정**(C6). 따라서 "완벽한 선택"보다 "빠른 기본값 + 격리로 낮춘 되돌림 비용"을 노린다.

### 1.1 평가 기준 (가중)

`[TA §1.2]`의 선택 기준을 게이트 결정용 가중표로 정리한다. 가중치는 F2P 모바일·P5 팀 맥락의 상대 중요도이며, 팀이 자기 상황에 맞게 조정할 수 있는 **출발점**이다.

| # | 기준 | 가중 | 왜 이 가중인가 |
|---|---|---|---|
| K1 | **결정론 코어 분리 용이성** | ★★★ | `float`/`Random`/`DateTime` 정적 차단 가능성. L1 순수성(`[MS §1.5]`)의 값이 여기서 결정 |
| K2 | **F2P 모바일 SDK 생태계 성숙도** | ★★★ | IAP·광고·어트리뷰션·분석·크래시(`[TA §8]`). F2P는 SDK 통합 실패 = 매출 손실 |
| K3 | **크로스플랫폼(iOS/Android→PC/웹)** | ★★★ | 단일 코드베이스(`[README P1]`, `[TA §12]`). WASM 결정론 재현성 포함 |
| K4 | **소규모 팀 생산성** | ★★★ | 단일 툴체인·핫리로드·채용 풀(P5) |
| K5 | **언어의 정수/고정소수 규율** | ★★ | `long`/체크드 산술 + Roslyn 애널라이저로 `[MS §1.5]` 컴파일 타임 강제 |
| K6 | **2D 스타일라이즈드 렌더 적합성** | ★ | 밝은 플랫 2D(`[README P3]`). 무거운 3D 불필요 → 렌더는 선택을 좌우하지 않음 |
| K7 | **라이선스·비용·장기 유지보수** | ★★ | 런타임 요금·라이선스 변동 리스크 |

### 1.2 후보 비교

`[TA §1.2]` 엔진 후보 평가표를 게이트 결정용으로 심화한다.

| 후보 | K1 분리 | K2 SDK | K3 크로스 | K4 P5 | K7 라이선스 | 핵심 리스크 |
|---|---|---|---|---|---|---|
| **Unity (C#)** | ★★★ 순수 C# 코어, IL2CPP AOT | ★★★ IAP/Ads/Firebase/attribution 전부 1급 | ★★★ iOS/Android/PC/WebGL 성숙 | ★★★ 대규모 채용 풀·문서 | ★★ 런타임 요금·라이선스 변동 이력 | 라이선스·비용 정책 변동 → **C6 격리로 대비** |
| **Godot 4 (C#)** | ★★★ 동일 C# 코어 전략 | ★★ 모바일 F2P SDK 생태계가 얇음(IAP/ads/attribution 상당 부분 자체 통합) | ★★ iOS/Android 지원·Web export 성숙 중, 2D 강함 | ★★ 경량·빠른 반복, 채용 풀은 작음 | ★★★ 오픈소스·라이선스 리스크 0 | SDK 통합 공수 = P5 팀의 매출 경로 리스크 |
| **Flutter/네이티브 UI + 별도 코어** | ★★ 코어 Dart/Rust 별도 검증 필요 | ★ 게임 SDK 생태계 아님 | ★★ UI는 강하나 게임 연출·파티클 약함 | ★★ UI 생산성 높으나 게임 느낌 부족 | ★★★ 오픈소스 | "게임 느낌"·연출 부족, 게임 SDK 부재 |

### 1.3 코어를 엔진과 분리해 결정을 가역으로 유지하는 전략

`[TA §0.2, §1.3]`의 4계층·모듈 경계를 **엔진 결정을 되돌릴 수 있게 만드는 장치**로 재확인한다.

```
Core.Sim   (C#, 순수, no-engine, no-float)      ← L1  ★ 엔진 결정과 무관, 재사용 자산
Core.Data  (C#, 스키마·직렬화·마이그레이션)      ← L1/L2 공용
Presentation.* (엔진 C#: 뷰·연출)                ← L2  ← 엔진 교체 시 재작성 대상
Services.* (엔진 C#: IAP/Ads/분석 어댑터)        ← L3  ← 어댑터 격리(포트)
```

- **핵심:** `Core.Sim`/`Core.Data`가 엔진 API(`Vector3`·`Time.deltaTime`·`Dictionary` 반복 순서 등)를 **한 줄도 참조하지 않으면**, Unity↔Godot 교체는 L2/L3만 재작성하는 국소 작업이 된다. 코어(수식·결정론·세이브)는 그대로 이식된다.
- **CI 강제(→ §5.4):** 어셈블리 의존 그래프에서 `Core.*`가 엔진/SDK 심볼을 링크하면 빌드 실패. 이 계약이 "가역성"을 문서 약속이 아닌 **기계 검증된 속성**으로 만든다.
- **함의:** D-102는 "지금 Unity냐 Godot냐"를 **당장 확정하지 않아도** D-103/104/105와 M2 코어 착수를 막지 않는다 — 코어는 엔진 없는 헤드리스 C#로 먼저 간다(→ §5.1).

### 1.4 권장 기본값 + 뒤집을 조건

- **권장 기본값:** **1순위 Unity(C#), 대안 Godot 4(C#). 어느 쪽이든 L1 결정론 코어 = 엔진 비의존 순수 C# 라이브러리. 코어 언어 = C#(엔진과 동일 언어).**
  - 근거: K2(SDK 성숙도)에서 Unity가 P5 팀의 통합 부담을 최소화 — F2P는 SDK가 매출 경로. C# 단일 언어는 마샬링/FFI 없이 단일 툴체인(K4)이고 Roslyn 애널라이저로 `[MS §1.5]` 무부동소수점을 컴파일 타임에 값싸게 강제(K1·K5). 2D 렌더(K6)는 두 엔진 모두 충분해 선택을 좌우하지 않는다. `[TA §1.2 설계 결정]`과 정합.
- **뒤집을 조건:**
  1. Unity 런타임 요금/라이선스 정책이 P5 손익을 실질 위협 → **Godot 4(C#)로 전환**(코어 이식, L2/L3만 재작성). 이 전환의 저비용이 곧 기본값을 안심하고 채택할 근거.
  2. C# 코어의 **WASM 결정론 동등성 또는 성능**이 스파이크(→ §5, `[TA §14-3·12]`)에서 미달 → **Rust 코어 + FFI**를 post-MVP 재검토(P5 이중 언어 부담과 저울질).
  3. 팀이 이미 Godot 숙련 + 필요한 F2P SDK가 자체 통합 가능 범위 → **Godot 우선**으로 K2 감점 상쇄.
  4. 관리 시뮬 UI 비중이 게임 연출을 압도하고 접근성/현지화가 최우선 → Flutter+별도 코어 재평가(단 게임 SDK·연출 리스크 수용 시).

## 2. D-103 — 해시 PRNG·믹싱 상수 동결 스파이크

> **막는 것:** 결정론 코어·세이브(교체 = 리플레이 비호환). **오너:** ENG. **성격:** **런치 전 동결 필수**(준-비가역).

### 2.1 왜 중요한가

`[MS §3.1]`: `roll(stream_id, c0,c1,c2,c3) = hash64(master_seed, stream_id, c0,c1,c2,c3)`. 이 **단일 64비트 정수 해시가 6개 RNG 스트림 전체의 토대**다:

| 스트림 | 좌표 | 의존 결과 |
|---|---|---|
| `APPLICANT` | (company_id, month/founding_seq, applicant_index, field_id) | 지원자 등급·스탯·리더십·잠재력 |
| `HIT` | (project_id,0,0,0) | 게임개발 흥행 등급(유일 대형 결과 RNG) |
| `ATTRITION` | (employee_id, day,0,0) | 자발적 퇴사 베르누이 |
| `PROGRESS_EPS` | (project_id, day,0,0) | 일일 진척 소변동 ε |
| `POSTING_VAR` | (posting_id,0,0,0) | 게시 보수 변동률 |
| `BOARD_REFILL` | (dept_id, day, slot_index,0) | 보충 게시물 티어·템플릿 |

해시 알고리즘·바이트 순서·믹싱 상수를 바꾸면 **모든 스트림이 동시에 달라진다**(→ §0.3). `[MS §3.1]` 명문: "해시 알고리즘·바이트 순서·믹싱 상수는 technical-architecture가 단일 고정한다(교체 시 리플레이 비호환)."

### 2.2 후보

| 후보 | 성격 | 강점 | 약점/주의 |
|---|---|---|---|
| **SplitMix64 파이널라이저 기반** | 정수 해시(믹서) | 단순·빠름·상수 공개·강한 아발란치. 6좌표 순차 믹싱 자연스러움 | 저비트 상관 가능성을 좌표 키잉 패턴에서 실측 필요 |
| **xxHash64** | 바이트열 해시 | 분포 품질 우수, 광범위 검증, 라이브러리 풍부 | 구현이 더 복잡, "임의 바이트 해시" 용도 → 좌표를 바이트로 직렬화하는 규약을 고정해야 함 |
| **PCG(해시 변형)** | 카운터→출력 | 통계 품질 최상급(PCG 계열) | 본래 스트림 생성기 → 무상태 좌표 키잉용 해시 변형의 구현·상수 고정 필요 |

- `[TA §13-①]` 이미 제시한 1순위: **SplitMix64 파이널라이저**. 좌표를 순차 믹싱(예: `x=seed; x=mix(x^stream); x=mix(x^c0); …`)하고 상수 `0x9E3779B97F4A7C15`·`0xBF58476D1CE4E5B9`·`0x94D049BB133111EB`를 **고정 매직 상수**로 문서화. 전 연산 wrapping u64.

### 2.3 평가 기준

| # | 기준 | 측정 대상 |
|---|---|---|
| P1 | **분포 품질** | 균등성·아발란치(1비트 입력 변화 → ~50% 출력 비트 변화) |
| P2 | **편향** | 좌표 키잉 특유 패턴에서의 상관: seed·stream 고정 후 `c0`(entity_id)만 0..N 증가, 또는 `c1`(day)만 증가시켰을 때 **저비트/상위비트 상관**. `[MS §2.3, §3.3]`의 소비 매핑(`roll mod FP`, `uniform32·PROB_ONE>>32`)에서의 매핑 편향 |
| P3 | **모바일+WASM 성능** | 롤당 나노초. 캐치업 핫패스(`[TA §9]`)와 만재 시뮬 예산 |
| P4 | **구현 단순성** | P5 팀이 세 플랫폼에서 동일 재현 가능하게 유지(K4) |
| P5 | **크로스플랫폼 바이트 동일성** | iOS AOT / Android / 에디터 / (후)WASM에서 같은 입력 → 같은 64비트 |

### 2.4 스파이크 절차

1. **구현:** 후보 3종을 `Core.Sim`에 동일 시그니처 `hash64(seed, stream, c0,c1,c2,c3)→u64`로 구현. 전 연산 wrapping(unchecked) u64, 좌표 믹싱 순서·엔디안 고정.
2. **통계 테스트:** 각 후보의 64비트 출력 스트림을 **PractRand / TestU01(SmallCrush→BigCrush) / Dieharder** 중 팀 가용 도구로 검정. 추가로 **좌표 키잉 실사용 패턴 검정** — (a) `c0`만 증가, (b) `c1`만 증가, (c) `stream`만 변경했을 때 출력 저비트 자기상관·교차상관을 측정(순차 스트림 검정으로는 놓치는 좌표 격자 편향을 잡는다).
3. **소비 매핑 편향:** 실제 소비 형태(`roll mod FP`로 `uniform01_fp`, `uniform_range` 정수 균등, `p_scaled` 베르누이 비교 `[MS §3.3]`)에서 χ² 균등성. 특히 `APPLICANT` 등급 inverse-CDF·`HIT` 버킷 경계 근처 편향.
4. **성능 벤치:** 저사양 실기(iOS/Android) + WASM에서 수천만 롤/초 측정, 캐치업 예산(`[TA §9]`) 대비.
5. **크로스플랫폼 골든:** 고정 입력 벡터(seed·stream·좌표 조합 수백 개) → 기대 64비트 표를 커밋. iOS AOT·Android·에디터·WASM에서 **바이트 동일** 검증.

### 2.5 수용 기준

- **P1/P2:** 선택 후보가 통계 검정 통과(치명 실패 없음) + 좌표 키잉 실사용 패턴에서 밸런스에 영향할 상관 없음. 특히 `HIT` 버킷 경계·`APPLICANT` 등급 경계에서 관측 분포가 명목 확률(`GradeDist`·`d_c*`, balance)에서 유의하게 벗어나지 않을 것.
- **P3:** 캐치업·만재 시뮬 예산(`[TA §9]`) 내.
- **P5:** 크로스플랫폼 골든 벡터 **완전 일치**(1비트도 불일치 불가). WASM 타깃 포함(`[TA §12, §14-12]`).
- 세 기준을 모두 만족하는 후보 중 **P4(단순성)**·기본값 지위로 SplitMix64를 우선.

### 2.6 권장 기본값 + 뒤집을 조건

- **권장 기본값:** **SplitMix64 파이널라이저 기반 `hash64`, 상수 3종 고정, 좌표 순차 믹싱, wrapping u64**(`[TA §13-①]` 정합).
- **뒤집을 조건:**
  1. 좌표 키잉 실사용 패턴(§2.4-2)에서 저비트 상관이 `HIT`/`APPLICANT` 분포를 명목값에서 유의하게 이탈시킴 → **xxHash64 또는 PCG 해시 변형**으로 교체(분포 우위가 성능 손실을 정당화할 때).
  2. 대안이 동등 분포에서 실측 성능 우위 + P5 유지 가능 → 성능 근거로 교체.
- **뒤집을 수 없는 시점:** 위 조건은 **동결 전(프로토타입)에만** 적용된다. 런치 후 교체는 리플레이 비호환 = 마이그레이션 이벤트(§0.3).

### 2.7 동결 체크리스트

동결(=골든 커밋) 시 아래를 문서·리포지토리에 고정한다:

- [ ] 알고리즘 명칭 + 파이널라이저 정의(의사코드)
- [ ] 매직 상수 전체(hex) 문서화
- [ ] 좌표 믹싱 **순서**(seed→stream→c0→c1→c2→c3) 고정
- [ ] 정수 폭(u64)·wrapping(unchecked)·엔디안 규약 고정
- [ ] 소비 매핑(`uniform01_fp`/`uniform_range`/베르누이) 규약 재확인(`[MS §3.1, §3.3]`)
- [ ] **크로스플랫폼 골든 벡터** 커밋(iOS/Android/에디터, 후 WASM)
- [ ] 결정 로그에 `[DL D-103]` A절 이동 + `[TA §13-①]` 역참조(→ §6)

## 3. D-104 — 고정소수 스케일 `FP` 동결 스파이크

> **막는 것:** 세이브·밸런스 정밀도. **오너:** ENG. **성격:** **런치 전 동결 필수**(준-비가역).

### 3.1 왜 중요한가

`[MS §1.5, §2.3]`: 게임플레이 결과에 영향을 주는 **모든 산술**은 고정소수 정수(`FP` 스케일, `i64` 보관)로 한다. `[MS §7]`의 함수 라이브러리에는 **복리형 곱**이 있다:

| 함수 | 형태 | 반복 곱 원천 |
|---|---|---|
| 라인 감쇠 `δ(n)` | `δ_min + (FP−δ_min)·ζ^n` | `ζ^n` — 누적 완료 `n`회(반복 프로젝트) |
| 레벨 요구 XP `XP_need(Lv)` | `X0·ψ^(Lv−1)` | `ψ^(Lv−1)` — 최대 레벨까지 |
| 훈련비 O-2 | `τ0·φ_train^s` (또는 `τ0·(s/S_ref)^q_train`) | `φ_train^s` — 스탯 상한까지 |
| 진척·품질·보상 | `base·e_team/FP·(FP+ε)/FP`, `q_raw` 볼록결합, `M×v_post×m_Q×coef×α_auto` | 다중 곱 사슬 |

각 고정소수 곱 `(a*b)/FP`는 나눗셈에서 **하위 자릿수를 절단**한다. 복리형은 이 절단을 **반복 누적**한다. **위험:** 누적 오차가 `q_raw`/성과 `y`를 품질 등급 절단점(`q_c1<q_c2`) 또는 성과 등급 절단점(`d_c1<d_c2<d_c3`) 너머로 밀면, 무한정밀 기준과 **등급이 역전**된다 — 밸런스 가드레일(`[GD §5.8]`) 경계에서 결과가 뒤바뀐다. `[TA §14-2]`·`[MS §12-2]`가 지목한 바로 그 질문이다.

### 3.2 후보

| 후보 | 스케일 | 정밀도(대략) | 강점 | 약점 |
|---|---|---|---|---|
| **10⁶ 정수** (`FP=1_000_000`, `i64`) | 십진 10⁶ | ~6 십진 자릿수 | `PROB_ONE=10⁶`과 동일 스케일, 밸런스 값이 사람이 읽기 쉬움(`[TA §2.6]` 현행 기본), 확률·통화 규약과 정합 | 복리형 곱에서 6자리 아래 절단 누적. 저정밀 |
| **Q32.32** (2⁻³² 스케일, `i64`) | 이진 2³² | ~9.6 십진 자릿수 | 정밀도 여유 큼, 이진 시프트 연산 빠름 | 밸런스 값 가독성↓, `PROB_ONE` 매핑 재정의 필요, 범위 헤드룸(정수부 32비트)이 십진 대비 다름 |

- **공통 오버플로 관리(후보 무관):** 다중 곱(`M×v_post×m_Q×coef×α_auto`)의 중간값은 **`i128`(System.Int128/직접 128비트) 누산 후 마지막에 1회 `/FP`·정수화**(`[MS §2.1, §TA §2.6]`). 오버플로는 이미 이 규약으로 막힌다 — **본 스파이크의 핵심은 오버플로가 아니라 정밀도(등급 역전)** 다.

### 3.3 평가 기준

| # | 기준 | 측정 |
|---|---|---|
| F1 | **최대 게임 기간 누적 오차** | 최장 시나리오에서 복리형 곱 결과 vs 무한정밀 기준의 편차 |
| F2 | **등급 역전 유무** | 편차가 `q_c*`/`d_c*` 절단점을 넘겨 등급을 바꾸는가(치명) |
| F3 | **표현 범위** | 최대 자금·XP·역량이 스케일 정수부에 수용되는가 |
| F4 | **오버플로 안전** | `i128` 중간 누산으로 다중 곱 안전(후보 무관 재확인) |
| F5 | **성능** | 곱/나눗셈·시프트 비용이 사이클 예산 내(`[TA §9]`) |

### 3.4 스파이크 절차 (최장 시나리오 오차 측정)

1. **기준 구현:** 유리수/십진 고정밀(예: Python `decimal`·`fractions`, 또는 C# `BigInteger` 유리수)로 `δ(n)`·`XP_need`·`φ_train^s`·`q_raw`·보상 사슬의 **무한정밀 참조값**을 계산.
2. **최장 시나리오 구성:** 각 복리형의 최댓값 구간을 밸런스 대역 상단으로 잡는다 — `n`=반복 프로젝트 누적 완료 최대(수천~수만 일 세션), `Lv`=최대 레벨(`level_cap`), `s`=스탯 상한. 계수(`ζ`, `ψ`, `φ_train`)는 balance의 대역 경계값으로 스윕.
3. **후보 계산:** 같은 시나리오를 `FP=10⁶`·Q32.32 각각으로 `(a*b)/FP`(또는 시프트) + `[MS §2.1]` 단일 반올림 규약대로 계산.
4. **오차·역전 측정:** 각 스텝에서 `|후보 − 기준|` 최대치. 특히 `q_raw`/성과 `y`가 절단점 근방일 때, 기준은 등급 X인데 후보는 등급 Y가 되는 **역전 케이스를 카운트**(경계 스윕: 절단점 ±ε 밴드에서 밀집 샘플).
5. **성능·범위:** 최대 자금·XP를 스케일에 대입해 정수부 오버플로 여부, 곱/시프트 벤치.

### 3.5 수용 기준

- **F2(치명):** 최장 시나리오·계수 대역 전 구간에서 **등급 역전 0건**. 즉 후보 스케일의 누적 오차가 어떤 가드레일 경계에서도 `q_c*`/`d_c*`를 기준과 반대편으로 넘기지 않을 것.
- **F1:** 최대 절대 오차가 밸런스가 요구하는 유효 자릿수(balance 소관) 이내.
- **F3/F4:** 표현 범위 수용 + `i128` 중간 누산으로 오버플로 없음.
- **F5:** 사이클 예산 내.
- **보조 완화책(후보 무관):** 복리형 경로에 한해 **내부 누산을 확장 정밀(예: `i128`에 추가 소수 비트 보관) 후 소비 직전 1회 정규화**하면 `FP=10⁶`로도 F2를 만족할 수 있다. 스파이크는 "스케일 상향"과 "확장 누산" 두 완화책 중 어느 쪽이 P5에 값싼지도 함께 판정한다.

### 3.6 권장 기본값 + 뒤집을 조건

- **권장 기본값:** **`FP=1_000_000`(10⁶ 정수, `i64`), 다중 곱은 `i128` 중간 누산 후 1회 정수화**(`[TA §2.6, §13-②]` 정합). `PROB_ONE=1_000_000`.
  - 근거: `PROB_ONE`과 동일 스케일이라 확률·통화 규약이 하나로 정합하고, 밸런스 값이 사람이 읽고 튜닝하기 쉽다(K4). `[MS §2.1]` "중간 반올림 누적 금지 + 원장 기입 직전 1회 정수화" 규약과 §3.5 확장 누산 완화책을 합치면 대부분의 복리형에서 등급 역전을 피할 수 있다.
- **뒤집을 조건:**
  1. 스파이크(F2)에서 **10⁶ + 확장 누산으로도 등급 역전이 남음** → **Q32.32(또는 더 높은 내부 정밀)로 상향**. `PROB_ONE` 매핑·밸런스 값 재표기 비용을 수용.
  2. 밸런스가 1e-6보다 고운 확률/계수 분해능을 요구 → 상향.
- **뒤집을 수 없는 시점:** 동결 전(프로토타입)에만. 런치 후 스케일 변경은 저장값 의미 변경 = 마이그레이션 이벤트(§0.3).

## 4. D-105 — 세이브 직렬화 포맷 스파이크

> **막는 것:** 세이브·마이그레이션 픽스처. **오너:** ENG. **성격:** 포맷 동결 + `save_schema_version` 마이그레이션 체인으로 진화 흡수.

### 4.1 왜 중요한가

`[TA §2.4, §3.3, §11]`: 세이브는 **바이트 재현성**을 가져야 한다 — 골든 상태 해시(`[TA §11]`)와 마이그레이션 골든 픽스처(N→N+1 라운드트립)가 이 위에 선다. 같은 상태가 매번 같은 바이트로 방출되지 않으면 결정론 회귀 테스트가 성립하지 않는다. 또한 포맷은 소규모 팀이 **스키마 진화**(필드 추가/제거)를 안전히 굴릴 수 있어야 한다(`[TA §3.3]` 단조 마이그레이션 체인).

### 4.2 후보

| 후보 | 성격 | 강점 | 약점/주의 |
|---|---|---|---|
| **FlatBuffers** | 스키마 기반 이진, 제로카피 | 스키마 진화(필드 추가/deprecate) 강함, 읽기 제로카피, 컴팩트 | 코드젠 스텝·의식(ceremony) 있음. **빌더의 vtable 중복 제거가 바이트 결정성에 영향** → 결정적 방출 검증 필요 |
| **MessagePack** | 이진 직렬화 | 단순·유연, C# 라이브러리(MessagePack-CSharp) 고성능 | 스키마 진화 수동(버전 필드 직접 관리). **맵 기반은 키 순서로 바이트 비결정 위험** → 정렬 배열·고정 필드 순서 강제 필요 |
| **Protocol Buffers** | 스키마 기반 이진 | 성숙·툴링 풍부 | 제로카피 아님, 필드 순서/기본값 규약이 바이트 결정성에 주의 필요 |
| **커스텀 정준 이진 writer** | 직접 레이아웃 | 바이트 레이아웃 완전 통제 = 결정성 최강 | 마이그레이션·진화 전부 수작업 → P5 유지보수 부담 최대 |

### 4.3 평가 기준

| # | 기준 | 측정 |
|---|---|---|
| S1 | **바이트 결정성** | 같은 상태 → 같은 바이트. 정준 순서 방출(정렬 배열, 맵 금지 `[TA §2.4]`)이 라이브러리에서 보장 가능한가 |
| S2 | **마이그레이션 용이성** | `save_schema_version` N→N+1 단조 체인(`[TA §3.3]`)을 값싸게. 결측=기본값, 제거=무시 |
| S3 | **스키마 진화** | 필드 추가/deprecate가 구버전 로드를 깨지 않는가 |
| S4 | **크기·성능** | 이진 크기(LZ4/zstd 후 수십~수백 KB `[TA §3.6]`)·파싱 속도 |
| S5 | **크로스플랫폼** | iOS/Android/에디터/WASM에서 동일 바이트·동일 파싱 |

### 4.4 스파이크 절차

1. **대표 세이브 구성:** 최대 규모 상태(10사 × 수백 직원 × 프로젝트·게시물·꼬리, 확정 롤 `resolved_Q`·지원자 카드 포함 `[TA §3.1]`)로 픽스처 생성. `master_seed`+`day`+`next_entity_id`만이 RNG 상태(`[MS §3.4]`).
2. **정준 방출 규약 구현:** 모든 컬렉션을 정준 키 오름차순(회사=slot_idx, 직원=employee_id …`[MS §1.2]`)으로, 맵 대신 정렬 배열로. `[TA §2.4]` 그대로.
3. **바이트 라운드트립:** `직렬화 → 역직렬화 → 재직렬화` 후 **바이트 동일** assert(S1). 후보 라이브러리의 결정적 방출 옵션 확인(FlatBuffers 빌더 결정성, MessagePack 정렬 배열 포매터).
4. **크로스플랫폼:** 같은 상태를 iOS/Android/에디터에서 직렬화 → 바이트 동일(S5). WASM 타깃 조기 확인.
5. **마이그레이션 골든:** `save_schema_version=1` 스키마 확정 후, 의도적 N→N+1 변경(필드 추가+deprecate) 스텝 하나를 구현하고, v1 픽스처를 로드→현재 승급하는 골든 테스트 작성(S2·S3).
6. **크기·성능:** LZ4/zstd 전후 크기, 직렬화/역직렬화 시간 벤치(S4, `[TA §3.6, §9]`).

### 4.5 수용 기준

- **S1(치명):** 라운드트립 **바이트 동일** + 정준 방출로 상태 해시 안정(`[TA §11]`).
- **S5:** 크로스플랫폼 바이트 동일(WASM 포함).
- **S2/S3:** N→N+1 마이그레이션 골든 통과, 필드 추가/deprecate 데모.
- **S4:** 압축 후 크기·파싱이 세이브 빈도(`[TA §3.6]`)·부팅 예산(`[TA §9]`) 내.
- JSON은 디버그/QA diff 덤프 전용으로만 병행(`[TA §2.4]`).

### 4.6 권장 기본값 + 뒤집을 조건

- **권장 기본값:** **FlatBuffers**(스키마 진화·바이트 레이아웃 통제가 마이그레이션 체인·골든에 유리, `[TA §2.4]` 후보 중 진화 강점). 헤더(`magic`, `save_schema_version`, `content_pack_version`, `balance_version`, `app_build`, `payload_len`, `hmac`) + 이진 페이로드 + HMAC-SHA256(`[TA §3.3, §3.4]`).
- **뒤집을 조건:**
  1. FlatBuffers 코드젠·빌더 의식이 P5 팀에 과부하 **또는** 결정적 방출을 값싸게 보장 못함(S1) → **MessagePack(정렬 배열·고정 필드 순서 포매터)** 로 전환.
  2. 어느 라이브러리로도 S1(바이트 결정성)이 흔들림 → **커스텀 정준 이진 writer**로 하강(유지보수 비용 대가로 결정성 확보).
- **주의:** 포맷을 바꿔도 `save_schema_version` 헤더·마이그레이션 체인 뼈대(`[TA §3.3]`)는 불변. 포맷은 "payload 인코딩"의 선택일 뿐, 버전 3종 분리(`save_schema` / `content_pack`·`balance` 핀 / `app_build`)와 정준 방출 규약은 후보 무관 고정이다.

## 5. 스파이크 실행 계획

### 5.1 순서·의존

핵심 통찰: **L1 코어가 엔진 비의존 순수 C#(§1.3)이므로, 언어 결정만 서면 PRNG/FP/포맷 스파이크는 헤드리스 C# 코어에서 엔진 최종 결정(D-102) 전에 병렬로 돌 수 있다.**

```
[언어 = C# 확정]  ← D-102의 "코어 언어" 부분만. 엔진(Unity/Godot) 최종은 뒤로 미룰 수 있음
        │
        ├───────────────┬───────────────┐   (병렬)
        ▼               ▼               ▼
   D-103 PRNG      D-104 FP        (D-105 준비)
   (헤드리스)       (헤드리스)        데이터 필드 타입은
        │               │           FP 스케일 확정에 의존
        └───────┬───────┘               │
                ▼                        ▼
        FP·PRNG 확정 → 데이터 필드 타입 안정 ──▶ D-105 세이브 포맷
                                                    │
   D-102 엔진 최종(Unity/Godot)  ← 코어 격리로 지연 흡수, L2 착수 직전까지 미룸
```

- **D-103·D-104:** 상호 독립, **완전 병렬**. 둘 다 순수 코어 스파이크라 가볍고 빠르다.
- **D-105:** 데이터 필드 표현이 **FP 스케일(D-104)** 에 의존(예: 고정소수 필드 폭)하므로 D-104가 방향을 잡은 뒤 착수하는 게 안전. `save_schema_version=1` 스키마는 PRNG 상태(`seed+day`)·확정 롤 저장 규약(`[MS §3.4]`)도 반영해야 하므로 D-103 방향도 참조.
- **D-102 엔진 최종:** 코어 격리(§1.3) 덕에 **표현 계층(L2) 착수 직전까지 지연 가능**. 언어(C#)만 먼저 고정하면 크리티컬 패스에서 빠진다(`[TA §14-9]`).

### 5.2 예상 공수 (상대)

절대 일정이 아니라 **상대 크기**(팀이 순서·인원 배분에 쓰는 신호):

| 결정 | 상대 공수 | 비고 |
|---|---|---|
| D-103 PRNG | **소~중** | 후보 3종 구현 + 통계/성능/크로스플랫폼 골든. 잘 스코프됨 |
| D-104 FP | **소~중** | 최장 시나리오 오차 하니스 + 등급 역전 스윕. 기준(고정밀) 구현이 주 |
| D-105 포맷 | **중** | 라운드트립 + 마이그레이션 골든 + 크로스플랫폼. 대표 픽스처 구성 포함 |
| D-102 엔진 | **중~대**(단 분산 가능) | SDK 통합 평가가 큼. "언어=C#"만 조기 확정하면 나머지는 L2 직전으로 분산 |

### 5.3 통합 Exit 게이트 — M2 세이브/코어 착수 조건

아래가 **모두 동결(=골든 커밋)** 되면 M2(세이브·코어 구현)를 착수한다:

- [ ] **코어 언어 = C# 확정**(엔진 최종은 미정이어도 무방, §1.3).
- [ ] **D-103 해시 PRNG 동결** — 알고리즘·상수·믹싱 순서·엔디안 고정 + 크로스플랫폼 골든 벡터 커밋(§2.7).
- [ ] **D-104 `FP` 스케일 동결** — `FP`·`PROB_ONE`·`i128` 중간 누산·(필요시)확장 누산 규약 고정 + 등급 역전 0 증빙(§3.5).
- [ ] **D-105 세이브 포맷 동결** — `save_schema_version=1` 스키마 + 정준 방출 + 바이트 라운드트립·마이그레이션 골든 통과(§4.5).
- [ ] 위 3종의 골든이 CI에 등록됨(§5.4).

> 이 게이트를 통과하면 세이브·마이그레이션·리플레이 골든의 **불변 기반**이 서고, M2가 그 위에 코어를 쌓을 수 있다. D-102 엔진 최종은 이후 L2 착수 게이트에서 별도로 닫는다.

### 5.4 동결 후 회귀 방지 (CI 훅)

동결을 상시 지키는 것은 문서가 아니라 CI다. `[TA §11]`의 훅을 4개 결정의 회귀 차단으로 매핑:

| CI 훅 | 지키는 동결 | 실패 = |
|---|---|---|
| **결정론 리플레이(골든)** | D-103·D-104 (같은 seed+로그 → 같은 상태 해시) | PRNG 상수/스케일 변경·부동소수 혼입 |
| **회사 순서 무관성 프로퍼티(DD-f)** | 코어 결정론(`[MS §9.6 DD-f]`, slot 순열 → 상태 해시 동일) | 회사 간 은닉 결합 |
| **바이트 골든(정준 직렬화)** | D-105 (상태 → 동일 바이트) | 비정준 방출·맵 순서 유입·포맷 회귀 |
| **세이브 마이그레이션 골든** | D-105 (N→N+1 라운드트립·구버전 승급) | 마이그레이션 손실 |
| **부동소수 금지 애널라이저** | D-102·D-104 (코어에 `float/double/Random/DateTime` 없음) | 결정론 오염원 유입 |
| **어셈블리 의존 그래프** | D-102 (Core.*가 엔진/SDK 심볼 미링크 → 가역성) | 엔진 결합으로 되돌림 비용 상승 |
| **크로스플랫폼 골든** | D-103·D-105 (iOS/Android/에디터, 후 WASM 동일) | 플랫폼 간 산술·바이트 불일치 |

- **상태 해시:** 세이브 스냅샷을 정준 순서로 직렬화해 안정 해시(`[TA §11]`). 파생 캐시 제외·정준 직렬화 범위는 `[TA §14-10]` 정규화 규칙 참조.

## 6. 결정 기록 훅

각 게이트가 확정되면 `decision-log.md`의 **B절(미결)** 에서 **A절(확정)** 로 이동한다. `[DL 갱신 규칙]` 준수. 이 결정들은 **기술 선택**이라 규칙 변경을 수반하지 않으므로 game-design 개정은 불필요(만약 확장 6종으로 표현 불가한 코어 변경이 필요해지면 그건 `[GD §8.3]` 개정 안건이다).

**확정 시 절차(각 D-102~105):**

1. **`decision-log.md` B절에서 해당 행 삭제, A절 표에 추가.** A절 컬럼: `ID | 결정 | 반영 위치 | 소유 | 날짜 | roadmap`.
   - 예: `D-103 | 해시 PRNG = SplitMix64 파이널라이저(상수 3종 동결) | technical-architecture §3.1·§13-①, tech-spikes §2 | ENG | (확정일) | M1.2.2`.
2. **반영 위치 역참조:** 확정 내용을 `[TA §13]` 인계 확정표(해당 ① `hash64`, ② `FP`)와 `[TA §14]` 열린 질문(해당 항목 해소 표기)에 반영하고, `[MS §11]` 인계 인터페이스의 "technical이 반드시 고정할 것" 목록에 실제 고정값을 링크.
3. **골든 커밋 링크:** 동결의 정의는 골든 테스트 벡터 커밋(§5.4)이므로, 결정 로그 행에 해당 골든 픽스처/CI 잡을 링크.
4. **roadmap 반영:** `roadmap-milestones.md`의 M1.2.x 완료 표기, M2 착수 게이트(§5.3) 상태 갱신.
5. **동결 결정(D-103·D-104)** 은 `production-qa-risk.md`의 "런치 전 동결" 추적 항목(`[README §2.6]`)과 `[DL D-111]`(밸런스 긴급 마이그레이션 예외)에 교차 링크 — 런치 후 변경이 마이그레이션 경계임을 명시.

- **D-102 부분 확정 처리:** "코어 언어=C#"만 먼저 확정하고 엔진 최종을 미룰 경우, A절에 D-102를 "부분 확정(언어=C#, 엔진 최종 = L2 착수 전)"으로 기록하거나, B절에 잔여 항목(엔진 최종)만 남긴다. 어느 쪽이든 M2 착수 게이트(§5.3)는 언어 확정으로 충족됨을 명시.

## 7. 열린 질문

본 문서는 4개 게이트의 평가 기준·후보·스파이크·수용 기준·권장 기본값을 제공했다. 아래는 스파이크 실행 중 팀이 답할 잔여 질문(규칙 질문은 `[GD §15]`, 구현 스펙은 `[MS §12]`, 기술 아키텍처는 `[TA §14]` 참조 — 본 목록은 그와 중복을 피하고 **게이트 실행 관점**만 남긴다).

1. **언어=C# 조기 확정의 타이밍** — 엔진 최종(D-102)을 L2 직전까지 미룰 때, "언어만 확정" 상태로 D-103/104/105·M2를 얼마나 안전하게 굴릴 수 있는가. 코어 격리(§1.3)가 실제로 지연을 흡수하는지 프로토타입으로 실증(`[TA §14-9]` 연동).
2. **좌표 키잉 편향의 판정 임계** — §2.4-2 저비트 상관 검정에서 "밸런스에 영향"의 정량 임계를 무엇으로 잡을지(`HIT` 버킷·`APPLICANT` 등급 관측 분포의 허용 이탈폭). balance의 `σ_hit`·`d_c*`·`GradeDist` 민감도와 연동(`[MS §12-9]`).
3. **`FP=10⁶` 확장 누산 vs Q32.32 상향의 손익** — §3.5 두 완화책 중 등급 역전 0을 P5에 더 값싸게 주는 쪽. 확장 누산이 코어 산술 API를 얼마나 복잡하게 하는지(`[TA §14-2]`).
4. **세이브 포맷의 결정적 방출 보장 비용** — FlatBuffers 빌더/MessagePack 포매터를 바이트 결정적으로 만드는 실제 공수(§4.4-3). 어느 라이브러리도 못 하면 커스텀 writer로 하강하는 손익분기(§4.6).
5. **WASM 동등성의 조기 검증 시점** — D-103·D-104·D-105의 크로스플랫폼 골든에 WASM 타깃을 M1 프로토타입에 포함할지, PC/웹 확장 시점(post-MVP)으로 미룰지. 조기 포함의 비용 대비 리스크 조기 발견 이득(`[TA §14-12]`).
6. **동결 골든의 유지 범위** — 동결 후 상태 해시 골든이 스키마 진화(D-105 마이그레이션)에서 견고하려면 어떤 정규화(파생 캐시 제외 범위)가 필요한지(`[TA §14-10]`와 공동).
7. **엔진 최종(D-102)의 SDK 스파이크 분리** — 엔진 후보별 F2P SDK(IAP/광고/어트리뷰션 `[TA §8]`) 통합 PoC를 별도 스파이크(BaaS/MMP `[DL D-106]`)와 어떻게 묶을지 — 엔진과 벤더 결정의 공수 공유 여부.
